Node.js 26 在 **2026 年 10 月 28 日，以 26.13.0、代號 Lithium 進入 LTS**。[官方發布公告](https://nodejs.org/en/blog/release/v26.13.0) 說明，這個版本調整了 LTS 中繼資料，其餘內容與 26.12.1 相同，預計持續提供更新至 2029 年 4 月。

審查升級時，這個區別很重要。進入 LTS 改變的是維護期間，並不代表執行環境可以直接沿用較早主要版本的假設。

同一份公告指出一個具體邊界：**官方 Linux 二進位檔從 Node.js 25 起便連結 libatomic**。從較早 LTS 升級的團隊，可能需要在 Linux 環境補上這個執行期函式庫。套件鎖定檔無法證明它已經存在。

本文分析這次發布，並提出升級審查順序；並未實際完成 Node.js 26 遷移、觀察到正式環境故障，或進行效能測試。上述版本號用來識別公告，不是建議把部署永久固定在這個修補版本。

## 一起審查執行檔與環境

[固定在該版本的建置文件](https://github.com/nodejs/node/blob/v26.13.0/BUILDING.md#official-binary-platforms-and-toolchains) 明確指出：官方 Linux 二進位檔執行時，必須能取得 libatomic。依發行版不同，套件名稱通常是 `libatomic` 或 `libatomic1`。文件也區分了支援平台與產製官方二進位檔所用的工具鏈。

因此，應用程式團隊審查的範圍，不應只有 `engines.node` 或 CI 的版本選項。應記錄實際執行應用程式的 runtime 成品、CPU 架構、基底映像，以及作業系統套件。

想像一個多階段映像：在工具齊全的建置環境成功編譯後，把 Node 複製到更精簡的執行映像。建置成功只證明了建置環境的某些條件，不能證明最終映像具備啟動該執行檔所需的函式庫。這是一種假設的失敗模式，不是宣稱某個特定映像有問題。

應優先取得最終成品的證據。在把應用程式測試當成第一個診斷工具之前，先在預定的執行映像與發布架構內，進行最小啟動檢查。

## 分開檢查啟動、依賴載入與行為

實用的審查順序可以分成三道檢查：

| 檢查 | 問題 | 保留的證據 |
| --- | --- | --- |
| Runtime 啟動 | 選定的執行檔能否在最終環境啟動？ | 精確版本、映像識別資訊、架構與指令結果 |
| 依賴載入 | 應用程式實際安裝的依賴能否載入？ | 確實使用原生依賴的 import 或啟動檢查 |
| 應用程式行為 | 應用程式是否仍符合既定契約？ | 相關整合測試、建置／匯出檢查與上線觀察 |

這個順序能縮小調查範圍。程序無法啟動時，不該先把問題當成框架退化。原生擴充套件載入失敗，也不該被模擬該邊界的單元測試掩蓋。即使 import 成功，仍無法充分說明應用程式在負載下的行為。

對靜態前端而言，相關的 Node 環境可能是建置 runner，而不是託管平台。應檢查產生匯出檔案的環境；若應用程式還有 Node 伺服器，也要檢查部署後的執行環境。相同的主要版本標籤，可能掩蓋這兩條路徑上的環境差異。

代價是額外的 CI 工作。讓啟動檢查維持精簡，把昂貴的行為測試放在應用程式真正會遇到的環境。針對實際交付的架構與映像變體建立小型矩陣，比測試所有可取得的映像更有用。

## 原生擴充套件還有另一道相容性邊界

Node-API 在這裡很有幫助，但它的保證有適用範圍。[Node.js 26.13.0 的 Node-API 文件](https://nodejs.org/docs/v26.13.0/api/n-api.html#implications-of-abi-stability) 描述了 Node-API 的 ABI 穩定性，也提醒其他 Node.js API 與擴充套件使用的外部函式庫，不一定具有相同保證。

不要把審查簡化成「這個套件用了 Node-API，所以升級沒問題」。應確認安裝程式選中了哪個二進位檔、它針對哪個平台，以及需要哪些外部函式庫。如果依賴使用其他原生 API，就要檢視它自己的相容性政策，不能直接套用 Node-API 的承諾。

這對由 agent 準備的升級也很重要。純 JavaScript 測試通過，是那些測試的有效證據，卻不是最終映像成功載入原生依賴的證據。應要求 agent 說明實際測到了哪個邊界、保留指令結果，而不是只提供籠統的相容性結論。

## 讓回復方案指向完整成品

有用的升級 PR 會列出新舊 runtime／映像組合、各自執行過的檢查，以及可以還原的發布成品。如果基底映像或作業系統套件也變了，只回復版本選項並不足以明確定義回復結果。

這不代表所有變數都要一起改。只要組合受到支援，評估 runtime 時固定基底映像，可以讓故障更容易定位。如果映像也必須更新，就把這個依賴關係寫清楚，並測試最終組合。

LTS 里程碑的實際價值，是讓支援規劃與相容性驗證一起進行。這次發布的 libatomic 提醒，具體指出 runtime 契約不只包含 JavaScript 原始碼與套件依賴圖，也包含啟動執行檔的環境。
