## 加一個篩選器

「加一個篩選器」聽起來仍是很小的前端需求。它短得足以放進工單標題，畫面上可能只多出工具列裡二十個像素的控制項。

但這項需求得從產品問題開始。哪些使用者需要它？要包含哪些資料？預設值是什麼？要不要和搜尋條件一起使用？團隊如何確認它真的有幫助？

產品經理要把這些問題整理成使用者目標、驗收條件、數據指標和 rollout 計畫。設計也不能只畫正常流程，還得定義空白、載入、錯誤和窄螢幕狀態。

工程端接著要決定篩選條件該放在 URL、本機狀態，還是共用狀態庫。API 可能需要新增查詢參數、更新 schema、處理分頁，並清楚回應查無資料的情況。

元件只是整項修改的一部分。測試、遙測資料、功能旗標、發布說明和回滾機制，可能同樣重要。

這不是站在未來回顧轉型的故事，而是 agentic engineering 剛起步的現場：Agent 已經進入交付流程，團隊卻還在摸索這套流程該怎麼運作。

## Agent 已經改變了什麼

Agent 可以搜尋程式碼庫、找到類似的篩選器、追查元件與 API 用戶端、修改多個檔案，再起草測試。以前開發者可能還在蒐集脈絡，它已經交出第一版程式碼差異。

這種速度已經改變日常工作。開發者可以先請 Agent 實作，檢查程式碼差異，指出漏掉的狀態，再要求它縮小修改，不必親手輸入每一行程式碼。

產品和設計也能更早驗證想法。可操作的預覽版本會在完整開發之前，暴露不清楚的預設值、遺漏的權限規則，或難用的行動版互動。

但輸出得快，不代表需求已經解決。Agent 可能複製既有錯誤、選錯抽象層、用自己的假設寫測試，或做出局部正確、整體卻破壞其他流程的修改。

新能力已經出現，配套的工作方式卻還沒成熟。

## 日常流程正在重整

好用的 Agent 工作流程從提示詞之前就開始。團隊要先寫清楚這次修改的使用者目標、影響範圍、預期狀態、API 行為、不處理的項目，以及發布前要提出的證據。

Agent 收到的應該是範圍清楚的任務和程式碼庫規範。它要交付可審查的程式碼差異，而不是在同一個 PR 裡重做元件系統、更換依賴套件，再改寫無關測試。

開發者要同時審查設計與實作。URL 還能分享嗎？伺服器端分頁有保留嗎？元件有使用既有設計系統嗎？權限由後端執行，還是只在 UI 隱藏？

自動化檢查要提供明確證據。契約測試驗證請求與回應的假設；元件與無障礙測試驗證各種狀態和鍵盤操作；端對端測試覆蓋使用者看得到的流程。

預覽環境讓產品、設計與工程查看同一個版本。功能旗標控制開放範圍，遙測資料反映使用情況和錯誤，回滾機制則處理正式環境與測試環境不同的意外。

上線後的資訊要回到下一輪。漏掉的邊界案例應該變成更清楚的驗收條件、測試資料、元件 API 或程式碼庫指引。

## 分工改變，責任沒有消失

Agent 工程實務不會取消專業責任，而是改變各角色投入注意力的位置，以及決策如何進入實作。

| 角色 | 新流程中的具體責任 |
| --- | --- |
| 產品經理 | 定義使用者目標、優先順序、驗收條件、成功指標、rollout 與後續決策 |
| 設計師 | 定義互動狀態、無障礙行為、響應式規則與產品用語 |
| 前端工程師 | 負責瀏覽器行為、狀態、渲染、效能、設計系統用法與 UI 驗證 |
| 後端工程師 | 負責領域規則、授權、資料完整性、API 契約與執行限制 |
| 全端工程師 | 沿著 UI、服務、資料、測試與發布流程追查完整需求 |
| 平台工程師 | 維護元件 API、型別化用戶端、程式碼庫指引、CI、預覽環境與可觀測性 |

這些責任會在交付過程中重疊。產品決策會影響 API 形狀，後端限制會影響互動設計，而前端錯誤狀態可能揭露服務契約無法區分「沒有結果」和「請求失敗」。

Agent 可以跨檔案帶著這些資訊工作，卻不能默默替團隊選擇要承擔哪一種取捨。這類決策仍要有清楚的負責人與可追溯的紀錄。

## 防護機制也是功能交付的一部分

團隊常把平台工作和功能交付分開看待。當 Agent 參與開發，兩者的關係就更難忽略。

定義清楚的元件 API，可以避免再做一個幾乎相同的篩選器。自動產生的用戶端讓 UI 程式碼跟上服務 schema。測試資料則能重現權限過期，或分頁後出現空頁的情況。

程式碼庫規範告訴 Agent 必須遵循哪些模式。CI 擋下型別錯誤、契約偏移、無障礙回歸和失敗的靜態匯出。預覽環境則讓審查者直接看到這次修改。

可觀測性補上合併前測試看不到的部分，例如真實資料的延遲、特定瀏覽器錯誤、異常的空結果，以及使用者到底有沒有使用這個篩選器。

防護機制也要符合風險。低風險的文案修改，不需要和新查詢路徑一樣多的證據。吵雜的測試和模糊的指令都會拖慢人與 Agent，因此同樣需要維護。

實際目標很簡單：讓預期的實作容易找到，讓高風險的實作容易被發現，也讓發布容易回滾。

## 我們已經一腳踏進新流程

多數團隊不會從全手動流程，一次跳進成熟的新模式。他們正在同一個迭代裡混用新舊工作方式。

一張工單可能由人親手完成，下一張從 Agent 產生的程式碼差異開始，第三張則只用 Agent 追查陌生的資料流或重現缺陷。

範圍仍在變動。團隊正在學習任務要附上多少脈絡、生成的修改應該多小、人該在什麼時候介入，以及哪些檢查能提供證據，而不只是增加儀式。

日常習慣也在改變。規劃開始包含給機器的指令，審查要追問生成的抽象設計，回顧則能把漏到正式環境的缺陷變成更好的測試資料、契約和程式碼庫規則。

前端開發仍是瀏覽器、API、狀態、測試與發布裡的具體工作。產品管理仍要具體處理目標、優先順序、驗收條件與上線後的學習。

Agent 工程實務把這些決策接到更快的實作上。我們已經踏進這條路，卻仍在一邊前進，一邊把腳下的路鋪好。
