[Python 3.15.0 於 2026 年 10 月 9 日成為穩定版本](https://www.python.org/downloads/release/python-3150/)，其中一項新增功能是明確的延遲匯入。這篇文章評估它的工程取捨，不是即時發布新聞，也不是已完成遷移的紀錄。本文沒有測量應用程式的加速幅度。

值得問的是初始化應該發生在哪裡。命令列工具可能還不知道使用者要產生報表還是查看說明，就先匯入成本很高的報表相依套件。延後匯入可能省去說明路徑上的工作，也會改變報表路徑初始化相依套件及發現錯誤的時間。

## 名稱可以先綁定，模組稍後才載入

[Python 3.15 語言參考文件](https://docs.python.org/3.15/reference/simple_stmts.html#lazy) 說明了 `lazy import module` 與 `lazy from module import name`。它們先綁定延遲代理物件，在第一次使用匯入名稱時才載入模組。`from` 匯入在需要時仍會載入整個模組，不會只執行被要求的那個定義。

這個語法僅限模組作用域，不能放在函式、類別主體或 `try`／`except`／`finally` 區塊內；星號匯入與 future statements 也不能延遲。檢查自動轉換時，這些限制很重要：替每個 import 加上關鍵字並不是有效的遷移策略。

若原始碼還必須讓較舊的 Python 解析，文件提供 `__lazy_modules__`：在模組層級列出完整模組名稱的容器，讓 3.15 將符合名稱的一般匯入視為延遲匯入。它保留舊語法，但仍需在每個支援的直譯器上驗證行為，不代表各版本的匯入時機相同。

## 失敗時機也是介面的一部分

文件指出，包含 `ImportError` 與 `SyntaxError` 在內的模組載入錯誤會在第一次使用時發生。因此，成功匯入應用程式的入口模組，不能證明所有延遲相依套件都能載入。

以選用的匯出指令為例，有用的驗收測試會在缺少選用相依套件的環境執行該指令，檢查錯誤訊息與結束狀態。成功執行 `--help` 驗證的是另一條路徑，兩者都重要，不能互相取代。

必須在啟動時偵測失敗的地方，保留立即匯入。若刻意延後載入，就在第一次使用的邊界檢查錯誤處理。不要捕捉所有例外，再一律宣稱缺少選用套件：相依套件自己的初始化也可能出錯，過寬的備援處理會掩蓋真正的缺陷。

這是建議的檢查方法，本文並未在 Python 3.15 上執行這個範例。

## 註冊可能就是匯入原本在做的事

[PEP 810 的副作用說明](https://peps.python.org/pep-0810/#how-do-lazy-imports-affect-modules-with-import-time-side-effects) 指出，匯入時的副作用也會延後，並建議使用明確的初始化函式，避免依賴匯入順序。

這會影響只為了註冊處理器而匯入的外掛模組。如果後續程式沒有使用它的匯入名稱，預期觸發註冊的事件就可能永遠不發生。其他測試若先立即匯入了外掛，反而可能掩蓋問題。

有限範圍的採用應先找出這類匯入。保留必要註冊的立即執行，或加入明確的初始化呼叫，並用全新程序測試。不要讓啟動效能修補變成未經審查的外掛探索機制重設計。初始化順序即使原本隱含在程式中，仍是應用程式行為。

## 測量真正支付成本的路徑

比較立即匯入與選定的延遲匯入時，固定相依套件版本與直譯器設定。記錄環境，重複測量全新程序；在既有程序中使用已載入的模組，回答的是不同問題。

| 路徑 | 應保留的證據 |
| --- | --- |
| 說明或其他輕量指令 | 產生有用輸出的時間，以及是否需要重型相依套件 |
| 首次使用相依套件的指令 | 包含初始化的端到端延遲，以及指令的實際結果 |
| 缺少或損壞的相依套件 | 診斷訊息、結束狀態，以及是否在預期邊界失敗 |
| 依賴註冊的指令 | 不靠其他測試先匯入，也能取得必要處理器 |

這些是建議的檢查項目，不是效能測試結果。即使完整指令沒有變快，更快的說明輸出仍可能有價值；第一次使用變慢，也可能不符合特定工作流程的需求。應依該流程的延遲預算判斷，不能把延後工作當成消除工作。

先選擇初始化契約已理解、且常用路徑不需要的相依套件。行為與測量結果支持後，再擴大範圍。明確的延遲匯入讓審查者看得到這個決定；真正要審查的是哪些事情現在可能晚一點發生。
