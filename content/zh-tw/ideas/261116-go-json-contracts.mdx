[11 月 4 日的 Go 公告](https://go.dev/blog/jsonv2)指出，`encoding/json/v2` 與 `encoding/json/jsontext` 已在 Go 1.27 成為穩定功能。這是審查 JSON 邊界的好時機，卻不是一次替換全部 import 的理由。本文提出審查計畫，沒有執行 Go 遷移或效能測試。

## 分開兩項決策

[版本說明](https://go.dev/doc/go1.27#encodingjsonv2)指出，既有 `encoding/json` API 持續受到支援，並透過新實作保留行為，但錯誤文字可能不同。因此，工具鏈升級與採用 v2 語意需要分開的證據。

先記錄每個邊界實際使用的工具鏈、import 與選項。改 import 前先執行既有契約測試。如果測試比對完整錯誤文字，應判斷文字究竟是公開契約，還是偶然的實作細節。不要為了讓建置通過就刪掉斷言；若契約真正要求的是行為，就改成檢查該行為。

## 分開測試輸入接受與輸出

[v2 參考文件](https://pkg.go.dev/encoding/json/v2)說明預設會拒絕重複的物件名稱與無效 UTF-8。這些預設值值得用來重新檢查過去接受的資料。同一套序列化程式產生資料後成功往返，不能取代其他產生端送入資料的邊界測試。

準備小型合成資料集：一般請求、重複名稱、格式錯誤的文字、大小寫不同的欄位名稱，以及缺少、null 或空集合值。逐項記錄預期接受結果與解碼意義，再另外核對輸出的 JSON 是否符合實際消費端的期待。測試資料不要包含個資、憑證或從正式環境複製的內容。

## 讓例外可以審查

先遷移一個邊界，並由能說明相容需求的負責人參與。如果某個選項保留舊行為，就記錄受影響的產生端、必要原因，以及移除條件。避免用全域相容設定掩蓋仍依賴舊行為的契約。

效能評估應另外進行：固定版本、輸入形狀與選項，再量測重要的工作負載。通過相容測試不代表加速，也不代表普遍安全。實用的審查應留下明確的接受矩陣、消費端檢查與回復決策，而不只是改過的 import 路徑。
