[Vite 在 2026 年 6 月 23 日的 8.1 公告](https://vite.dev/blog/announcing-vite8-1)中介紹了實驗性的 chunk import maps。本文依據 11 月 10 日查閱的官方文件，評估這項既有功能；不是新版本快訊，也沒有宣稱實測效能提升。

真正值得回答的是：減少不必要的 chunk 變更，是否值得增加一項必須驗證的發布行為？更新量變小固然有價值，但讀者在部署前、部署中與部署後，都仍須載入一致且可運作的應用程式。

## 把 chunk 身分與目前 URL 分開

[Rolldown 文件](https://rolldown.rs/reference/InputOptions.experimental#chunkimportmap)說明了不依賴內容雜湊的 chunk key。Import map 將這些 key 對應到產出的檔案，減少僅因依賴檔名改變而造成的連帶變更。

這個機制適合用一個明確的實驗來評估：只修改一個小型葉節點模組，再比較前後兩次建置。哪些檔案改變？壓縮後的變更位元組有多少？代表性路由實際會請求其中哪些檔案？只計算改名檔案數，可能誇大很小或根本不會在該路由載入的檔案所帶來的效益。

除了刻意修改的內容，固定原始碼版本、鎖定檔、建置設定與壓縮設定；分別比較關閉與啟用選項的結果。這是建議的量測方式，本文沒有實際執行 Vite 建置實驗。

## 保留實驗功能的界線

目前的 [Vite 選項文件](https://vite.dev/config/build-options#build-chunkimportmap)將 `build.chunkImportMap` 標示為實驗性、預設關閉，且需要 `import.meta.resolve` 支援。因此，發布審查應列出實際支援的瀏覽器，不能把建置成功視為瀏覽器相容性的證明。

[功能指南](https://vite.dev/guide/features#chunk-import-map-optimization)也指出，CSS 與資產不完全適用這項最佳化。變更資產仍可能使引用它的 chunk 改變，只是失效不一定繼續傳遞給上層引用者。

這些限制適合用小範圍試驗處理，而不是一次套用到所有應用程式。比較時同時包含純 JavaScript 修改與資產或樣式修改。若平常發布的大部分變動來自圖片與樣式，JavaScript 的結果未必代表日常更新成本。

8.1 公告也提醒，當時 `experimental.renderBuiltUrl` 無法與此選項搭配。若交付流程依賴自訂 URL 改寫，規劃採用前應先驗證審查中的確切版本是否支援這個組合。

## 把文件與它引用的檔案視為同一次發布

有了對應表，不代表舊文件會自動變成新版本。已開啟的分頁仍可能需要原本版本的檔案。因此，即使公開 URL 相同，新分頁與舊分頁也是不同測試情境。

Vite 的[正式環境建置指南](https://vite.dev/guide/build#load-error-handling)討論了舊部署資產被移除後，動態載入可能失敗，並建議以 `Cache-Control: no-cache` 讓 HTML 重新驗證。這是發布審查的背景，不代表一個快取標頭就能解決所有舊分頁情境。

評估採用時，記錄主機如何準備新檔案、切換入口文件、保留舊檔案，以及還原前一版。檢查該主機實際回傳的標頭與資產行為；不要假設應用程式設定能控制 CDN。這是維運審查建議，不是變更本站的主機或安全設定。

可以用一個簡短的驗收表區分這些情境：

| 情境 | 建議保留的證據 |
| --- | --- |
| 更新後開啟全新瀏覽器 | 入口文件、請求的 chunk URL 與成功呈現的路由 |
| 更新前已開啟分頁，之後進入延遲載入路由 | 舊引用仍能解析，或應用程式提供明確的復原方式 |
| 發布期間仍使用快取文件 | 在已說明的保留期間內，其引用檔案仍可取得 |
| 回復版本 | 還原的文件與必要檔案組成可運作的前一版 |

舊分頁測試應包含真實合理的未完成操作。強制重新整理讓畫面恢復正常，卻遺失表單內容，與安全復原不是相同結果。應明確決定這項行為，而不是把任何重新載入都當成成功。

## PR 需要兩種證據

最佳化審查應同時包含快取比較與發布一致性檢查。記錄確切 Vite 版本、選項值、受控的原始碼變更、壓縮後的變更位元組、瀏覽器覆蓋範圍，以及檔案保留與回復假設。把失敗與尚未測試的組合和正面結果一起呈現。

Agent 可以協助蒐集這些產物，但 bundle 變小的敘述，不能證明舊工作階段能跨越部署。讓採用過程可回復；若證明的效益不值得相容性與維運工作，就維持關閉。目標是減少不必要的傳輸，同時讓發布行為仍能清楚說明。
