[2026 年 9 月 9 日發布的 React 19.3](https://react.dev/blog/2026/09/09/react-19-3)將 Fragment refs 列為穩定功能，讓程式在不增加 DOM 包裝元素的情況下進行命令式操作。本文是 11 月 12 日對既有功能的評估，不是新版本快訊，也不是已執行的遷移報告。

如果容器只是為了放置 ref 而新增，它可能適合移除。但若容器承擔有用的版面或語意責任，就需要另一種判斷。審查應從元素的工作開始，而不是從能刪除多少元素開始。

## 把操作介面與容器分開思考

假設一個結果元件會回傳標題與數個控制項。父層可能需要把焦點移入結果，同時又希望子元素直接參與外層版面。這是值得評估 Fragment ref 的情境。

修改前，列出現有容器承擔的責任：CSS 選擇器、定位假設、事件處理器、無障礙名稱及測試定位方式。決定哪些責任可以消失，哪些仍需要實際元素。命令式操作介面本身不能取代標題、具名區域或表單分組。

保留承載預期意義的標記。如果問題只是元件 API 不方便，應比較「讓元件公開一個有限的動作」與「讓呼叫端操作較大的群組」。減少包裝元素，不應悄悄擴大責任範圍。

ref 必須使用明確的 `<Fragment ref={...}>` 語法，不能使用 `<>`；取得的操作物件是 `FragmentInstance`，不是 `HTMLElement`。詳見 [API 參考文件](https://react.dev/reference/react/Fragment)。

## 焦點目標是產品決策

[Fragment 參考文件](https://react.dev/reference/react/Fragment)指出，`focus()` 會以深度優先方式搜尋巢狀子元素中的第一個可聚焦節點；事件監聽與觀察器則針對第一層 DOM 子元素。

在結果元件中，「聚焦結果」究竟是什麼意思？是主要動作、失敗後的重試按鈕，還是載入完成才出現的控制項？只有當所有相關狀態的目標都符合意圖時，通用群組操作才有幫助。

可規劃一個含兩個控制項的測試，再把新控制項插入前方。接著測試第一個控制項停用、結果為空，以及條件式錯誤動作。記錄使用者觸發操作後實際取得焦點的元素，也檢查一般 Tab 導覽：命令式移動成功，無法證明其餘鍵盤路徑合理。

如果不論子元素順序如何，都必須聚焦特定動作，就應把目標寫入元件契約。不要讓偶然的原始碼順序變成後續貢獻者不知道的限制。

## 分別審查事件與觀察

不要把「群組的 ref」理解為「一個普通容器元素」。對事件整合，記錄處理器對 target 的假設、傳播方式，以及哪一層負責註冊與清理。在取代舊容器上的監聽器前，先比對所選 API 是否符合這些預期。

對觀察器整合，決定應用程式需要整個區域的一個結果，還是個別成員的觀察結果。寫清楚這些結果如何轉換成載入內容或更新可見狀態等產品決策。彙整規則應明確設計，不該因為簡單展示中回呼恰好執行一次，就自行推定。

測試掛載、增刪子元素及卸載群組，並加入重複循環，讓重複註冊或過期觀察可以被看見。這些是建議檢查項目，不是本文已完成的 Fragment-ref 實驗結果。

## 用不同證據審查同一個改動

| 關注點 | 建議的前後比較證據 |
| --- | --- |
| 版面 | 相同外層 grid 或 flex 版面、窄視窗與長內容 |
| 意義 | 預期的標題、名稱與分組仍然存在 |
| 焦點 | 載入、錯誤、空結果及重新排序狀態中的指定目標 |
| 事件與觀察 | 重複變動時，回呼、彙整與清理符合預期 |

截圖可以呈現移除容器是否改變版面；鍵盤操作紀錄可以呈現焦點去了哪裡。兩者無法互相證明。除了這些證據，也應檢視最終 DOM 與相關無障礙資訊，並在審查中保留失敗結果。

採用決策應記錄確切的 React 與整合版本，並保留小範圍回復方式。本文沒有執行依賴升級、效能測試或無障礙稽核。值得追求的是更清楚的元件契約，並保留必要標記，而不是全面把容器換成 Fragment。
