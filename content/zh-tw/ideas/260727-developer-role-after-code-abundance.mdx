我不再認為 agent 時代最核心的問題，是它們能不能寫出有用的程式碼。它們能。

真正困難的是：當產生看似合理的實作，比判斷它是否值得留在系統裡還便宜時，我們該怎麼工作？

## 瓶頸已經轉移

過去，工程師有很大一部分時間花在把意圖化為可運作的變更。agent 壓縮了這段迴圈。

它們能探索 repository、起草實作，再依據回饋快速修正。改變的不只是打字速度，也是變更交到團隊手上的速度。

當程式碼變得充裕，控制複雜度才成為工程工作。

稀缺的資源變成判斷力：該改什麼、哪些地方必須維持穩定，以及 pull request 的新鮮感退去後，系統還承擔得起什麼。

## 程式碼的重要性正在改變

程式碼仍然是人需要理解的產物，但它也愈來愈是機器必須能安全檢視、修改、測試與復原的基礎。

因此，明確的邊界、可預期的結構、局部變更、可執行的檢查、repository-native 的脈絡，以及清楚的所有權與回滾路徑，價值都更高。

人類可讀性沒有變得可有可無；它成為更廣泛要求的一部分：程式碼庫必須可由人治理，也能讓機器安全運作。

若 agent 能改一個系統、團隊卻說不清它如何運作，那不是適應力，只是改得很快。

## 便宜的程式碼可能帶來昂貴的複雜度

agent 降低了新增程式碼的成本，卻沒有降低長期擁有它的代價。

一個看似合理的實作，仍可能引入不需要的抽象、重複既有概念、擴大變更範圍，或遮蔽未來維護者和 agent 都必須重新理解的意圖。

生成成本趨近於零；所有權成本卻沒有跟著下降。

因此，生成的 slop 不只是表面問題。每一層沒有理由的複雜度，都會多出一條要學的規則、一個要測試的分支，以及未來變更可能意外失敗的位置。

程式碼出現得越快，我們越要慎重決定哪些複雜度可以留下。

## 通過檢查不代表變更足夠好

validation 與 verification 提供不可或缺的證據：預期行為、型別一致性、建置相容性，以及已知不變條件是否成立。

但它們無法判定抽象是否必要、變更範圍是否超出實際需要，或程式碼是否已用最清楚的方式表達意圖。

verification 問的是變更能不能運作；review 問的是這是不是值得我們長期承擔的變更。

機械式檢查應該提早且頻繁地執行；成功不等於可以跳過質性的 review。

這不是不信任自動化，而是讓自動化承擔它真正能做的工作，同時保留可見的設計判斷。

## 開發者成為品質關卡

把這種轉變簡化成「開發者是 agent 的協調者」太淺了。

開發者要定義意圖和限制、拆解工作、界定 agent 的任務範圍、review 並修正實作、撰寫 guardrail 和驗收條件，並承擔 production 的後果。

這個角色需要在每個邊界主動介入。好的 prompt 可以啟動工作，但不能取代拒絕薄弱設計、縮小 diff、移除抽象，以及要求提出與風險相稱的證據等判斷。

## Agentic 開發的分階段關卡

要讓 agent 的速度真正轉化為價值，workflow 需要一連串明確關卡：

```text
意圖
  -> 設計關卡
  -> 範圍受限的 agent 任務
  -> 小而可 review 的變更
  -> 人工 review 與修正
  -> validation 與 verification
  -> merge
  -> production 回饋
```

順序很重要。低成本的檢查可以在整個迴圈中執行，但最後的 validation 與 verification，必須在嚴謹的人工 review 與修正完成後進行。

review 回饋可以把工作送回 agent；production 回饋則應強化下一次的設計關卡和任務邊界。

這不是瀑布式流程，而是一個讓速度始終與責任歸屬綁在一起的受控迴圈。

## 在 slop 變成架構之前擋下它

最有效的 guardrail，是在生成結果固化成既定做法前，就把日常工程紀律落實在流程中。大量生成程式碼前，先要求設計或變更契約。

拒絕過大或範圍不清的 pull request；設定檔案、dependency 與架構邊界；寧可拆成幾個彼此連貫的小變更，也不要一次提交包山包海的大改動。

要求 agent 回應 review 回饋並簡化輸出，而不是只再疊上一層 patch。把無法說明的複雜度視為需求沒有達成。

merge 之前，要求與風險相稱的證據：並非每個變更都需要相同的證明，但每個變更都要能交代為何應該進入 `main`。

## Senior developer 與 engineering lead 的工作如何改變

對 senior developer 而言，花在打出第一版實作的時間可能變少，花在塑造邊界、追問抽象、修正輸出，以及改善讓人和 agent 都能安全修改的系統介面上的時間則變多。

工作更偏向架構，但不會因此脫離實作。

對 engineering lead 而言，交付系統必須避免生成速度超過 review 能力。團隊該衡量的是經過 review 與 verification，且可維護的成果，而不是生成行數、agent 執行次數或 pull request 數量。

團隊能投入 review 與修正的量能，本來就是系統真正產能的一部分。

## 工程槓桿的新定義

最強的 agentic 工程師，不是產出最多程式碼的人，而是能把機器速度轉成可維護變更、又不讓複雜度悄悄累積的人。

工程槓桿，是預防、塑造並安全擁有複雜度的能力，而不是生成程式碼的數量。
