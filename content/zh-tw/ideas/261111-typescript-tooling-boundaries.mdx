[2026 年 10 月 20 日公告](https://devblogs.microsoft.com/typescript/announcing-typescript-7-1-beta/)介紹了 TypeScript 7.1 beta 與預覽版 API。[官方首頁](https://www.typescriptlang.org/)在 11 月 11 日仍將 7.1 列為 beta。本文提出評估方法，沒有執行遷移或效能測試。

命令列型別檢查成功，只回答了那個命令能否檢查那個專案。它無法證明自製文件產生器、lint 整合或編輯器輔助工具仍然理解同一個專案。這些整合是不同的使用端，各有輸入與輸出，應分別驗收。

## 先盤點使用端，再調整套件

[7 月 8 日的 TypeScript 7.0 發布公告](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)說明，7.0 沒有程式化 API，並為既有工具介紹了 TypeScript 6 相容套件。因此，較新的編譯器執行檔與較舊的 API 使用端，可以是刻意保留的工具鏈組合。

從實際依賴圖與腳本開始，為每個使用端記錄解析到的編譯器套件、使用執行檔還是 API、設定來源，以及輸出產物。不要假設更改最上層依賴，就會按預期更新工具內部的依賴或 peer resolution。

盤點表要足夠精簡，讓人能審查。「文件產生器及其宣告檔輸出」是有用的一列；只有「支援 TypeScript」則不足以判斷。移除可運作的相容路徑前，先確認各整合維護者明確支援的版本範圍。

## 明確指定設定的責任歸屬

Beta 公告的 API 編譯範例接收明確的檔案與選項，不會載入 `tsconfig.json`。把範例帶入專案工具時，還需要決定設定如何取得。

評估整合時，選擇刻意限縮的輸入契約，或沿用專案既有的設定語意，再測試這項選擇。案例應包含繼承設定、預期根目錄以外的檔案，以及只在建置期間存在的產生式宣告檔。先比較實際輸入與選項，再比較診斷數量。

這對自動審查尤其重要：檢查錯誤檔案集合卻顯示綠燈，比清楚失敗更容易誤導。讓命令輸出足以識別設定與原始碼版本的非敏感資訊，但不要把原始碼全文或環境變數傾倒進報告。

## 讓失敗與清理可以被觀察

Beta API 要求釋放 API 與 program 資源。長時間運行的整合應把資源歸屬視為正確性的一部分。

可以規劃一個小型重複工作測試：開啟專案、取得結果、結束請求，再重複執行。在成功案例之間加入失敗與中斷，確認後續工作仍能完成，每條離開路徑都有清理。如果要評估資源滯留，應觀察整段流程的程序記憶體；啟動後的一次低用量讀值，無法證明資源已釋放。

另外決定診斷結果屬於哪次請求。如果另一次編輯已使請求過時，呼叫端不應把舊結果當作最新答案。給請求加上原始碼版本或世代識別碼，測試完成順序顛倒的情境。這是整合設計建議，不代表 TypeScript 會自動替工具實作這個政策。

## 訂出可回復的驗收決策

| 審查項目 | 建議證據 |
| --- | --- |
| 輸入 | 解析到的套件、設定、根檔案與產生式檔案假設 |
| 輸出 | 預期診斷、原始碼位置，以及適用時的輸出產物 |
| 重複工作 | 成功、失敗與中斷請求之後，仍可成功處理新請求 |
| 回復 | 舊 lockfile 與使用端實作仍能重現已接受的結果 |

先比對正確性，再計時。若效能是評估目標，記錄確切預發行版本、機器限制、原始碼版本、快取狀態與工作負載。單次檢查應與重複的編輯器或服務請求分開。廠商公布的加速數字不是這個整合的量測，本文也不主張任何加速成果。

保留現有工具，同時以小範圍 fixture 評估 beta，也可以是合理結論。逐項記錄哪個使用端通過、失敗或尚未測試。採用前重新確認發布狀態與整合支援；預覽 API 適合可回復的試驗，不足以宣稱所有依賴工具都已完成遷移。
