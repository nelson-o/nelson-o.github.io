## 加入一個篩選器

「加入一個篩選器」曾經是很常見的前端需求。這句話短得足以成為工單標題，最終看得見的結果，可能只佔工具列上的二十個像素。

這不是某個真實專案的完整重述，而是由許多前端程式碼庫裡反覆出現的修改組合而成。那時，編碼 Agent 還沒有進入日常工作流程。

第一個問題通常不是如何渲染控制項，而是這個篩選器究竟代表什麼。它應該包含哪些紀錄？是否和現有搜尋組合？重新整理後是否保留？狀態要不要寫入 URL？預設值由誰決定？API 很慢、結果為空，或者舊瀏覽器對輸入控制項的處理不同時，又該怎麼辦？

一個控制項就可能暴露產品歧義、資料語意、互動設計、狀態所有權和發布風險。程式碼只是整段工作裡最看得見的中間部分。

## 交接鏈

在 Agent 時代之前，角色邊界往往沿著實作工作堆積的位置形成。

設計師描述預期互動，前端開發者把它翻譯成瀏覽器行為，後端開發者提供或修改查詢契約。當兩端無法對齊時，全端開發者負責跨越縫隙。QA、審查者和發布負責人再確認這些部分能否整體成立。

這些邊界很有用，但也形成了一條交接鏈。每個人都要重新建構同一個問題的不同部分。缺少 loading state，就退回設計；查詢無法表達，就退回後端；測試發現不一致，就帶著截圖、payload 和重現步驟沿著鏈條往回走。

角色名稱不只描述專業能力，也描述昂貴的人類工作會在哪裡排隊等待。

## 看不見的工作

修改元件之前，前端開發者必須先建立一個心智模型。

這意味著找到路由、追蹤元件樹、定位狀態儲存、閱讀 API client、查看類似篩選器在其他地方如何運作，並從舊 pull request 裡尋找從未進入文件的決策。還要比較設計稿和現有產品，判斷哪一個才代表現實。

瀏覽器分頁變成工作記憶：框架文件、issue tracker、相容性表格、network trace，以及只解決一半問題的範例。剩餘的空白由對話填補。等真正開始實作時，困難工作大多已經發生，卻很少出現在 diff 裡。

元件渲染出來之後，循環還會繼續。開發者嘗試不同篩選組合、重新整理頁面、改變 viewport size、檢查 request、修復測試、等待 CI、回應 review，再檢查部署後的結果。「完成」不是程式碼已經存在，而是足夠多的不確定性被消除，讓修改值得信任。

## 平台工作早已不可缺少

團隊無法只靠個人能力擴展這類工作。即使在 Agent 時代之前，前端平台投入也已經是必需品。

設計系統減少重複決策；元件庫保存無障礙與互動行為；型別化 API client 讓契約漂移可見；本機工具縮短回饋循環；預覽環境讓審查不再依賴每個人重現分支。CI、瀏覽器測試、視覺回歸與可觀測性，則把預期轉化為可以重複執行的檢查。

這些系統有時被視為功能交付之外的次要工作，但正是它們讓功能交付可以持續。鋪好的道路讓開發者不必為每個需求重新建構按鈕、表單、loading state、建置設定和測試設定。

平台主要放大人類的實作能力。收集脈絡、選擇路徑、編寫修改、解釋檢查結果，仍然由人完成。平台只是讓這條手動循環更快、更一致。

## UI 建構不再稀缺

Agent 與 UI builder 改變了這條循環的經濟性。

Agent 可以搜尋儲存庫、找到類似篩選器、加入元件、更新狀態、接入查詢參數，並在一次處理中起草測試。它可以在團隊過去完成第一個實作之前，就生成多個版本。曾經需要長時間機械專注的跨檔案修改，現在變得便宜。

這不代表工作會自動正確。消失的是實作的稀缺性。產出一個看起來合理的介面，不再像過去那樣是主要限制。

這個區別很重要，因為工程角色有一部分是圍繞「誰能產出哪種成果」組織起來的。當產出變得便宜，前端、後端和全端的舊邊界就不再具有同樣的解釋力。更困難的邊界會移向：誰定義約束，以及如何驗證結果。

## 角色邊界開始移動

專業分工不會消失，但重心會改變。

| 角色 | Agent 時代之前的中心 | Agent 時代帶來的壓力 |
| --- | --- | --- |
| 設計師 | 產出介面意圖並交給實作 | 讓狀態、約束、token 與品質標準能被生成系統理解 |
| 前端開發者 | 實作面向瀏覽器的行為 | 塑造 UI 架構、平台規則與介面特有的驗證方式 |
| 後端開發者 | 實作服務與資料契約 | 編碼領域不變量、運行限制與契約，讓生成的 client 無法輕易違反 |
| 全端開發者 | 透過實作兩端跨越邊界 | 編排跨邊界修改，並驗證整合後的行為是否解決需求 |
| 平台開發者 | 加速人類開發者 | 約束、引導、觀察並驗證大量生成的修改 |

決定層級、互動、無障礙和產品語言時，設計師的專業能力仍然重要。前端專家仍然理解瀏覽器、渲染、效能與互動狀態的失敗模式。後端專家仍然負責領域行為、安全、資料完整性與運行後果。全端工程師仍然能看見任何單側視角都會遺漏的整合缺口。

真正改變的是，各角色需要親手建構多少內容，才能表達自己的專業判斷。工作可以從產出一個實作，轉向定義一個能夠安全產出許多實作的系統。

## 平台成為控制平面

在 Agent 工作流程裡，前端平台不再只是生產力層，而會成為控制平面。

設計 token 縮小視覺選擇範圍；元件 API 提供認可的互動模式；schema 定義有效的資料形狀；儲存庫指令公開本地約束；標準範例展示預期架構；測試 fixture 讓邊界情況可以重現；CI 政策決定一項修改繼續前進之前必須提供哪些證據。

Agent 能沿著明確路徑快速前進，是因為這條路徑承載了人類之前編碼進去的判斷。沒有這條路徑，速度只會帶來局部發明：幾乎相同的元件、不一致的狀態模型、無法審查的 diff，以及只能證明生成實作與自身一致的測試。

這也改變了平台工作的價值。一次平台改進，不再只是為每個記得使用它的開發者節省幾分鐘；它可以塑造進入儲存庫的每一個生成修改。槓桿更大，但糟糕預設值的代價也更大。

## 更少的人類實作，更多工程化驗證

如果 Agent 用更少的人類工作產出更多修改，驗證就不能繼續停留在最後的手動作業。人類的審查注意力，無法和生成輸出以同樣速度擴展。

解決方式不是要求開發者審查更多程式碼，而是工程化更強的證據：

- 驗證前端與後端假設的契約測試
- 發現版面與設計系統漂移的視覺回歸
- 檢查語意與互動的無障礙測試
- 覆蓋使用者可見流程的端到端測試
- 支援真實檢查的預覽環境
- 觀察只在發布後出現行為的可觀測性
- 限制風險的 scoped diff、發布控制與回復路徑

這些檢查本身就是開發工作。它們需要和過去功能實作同樣的謹慎：判斷什麼重要、建模失敗、選擇有效邊界，並保持訊號可靠。

檢查也不是越多越好。生成的修改可以在解決錯誤問題的同時通過淺層測試。龐大的測試套件也可能變得緩慢或嘈雜，最終失去信任。哪些屬性必須是不變量、哪些結果需要觀察、哪些例外值得投入注意力，仍然需要人類決定。

有價值的轉變，是從反覆檢查每個機械步驟，轉向把規則編碼一次，再持續套用。

## 新的稀缺工作

問題定義仍然是人類工作，但它只是新角色的一部分。更大的機會，是讓工程判斷可以重複利用。

這包括在生成之前解決歧義，強化團隊反覆產生分歧的契約，以平台原語取代又一個一次性元件，並在缺陷逸出後改進驗證。它也包括處理例外：陌生風險、衝突約束、生產事件，以及現有控制平面無法給出可信答案的修改。

前端開發者面對的問題，會比「我能否建構這個介面？」更廣：系統是否讓預期介面容易生成？是否讓錯誤介面難以發布？其他開發者、設計師、後端工程師或 Agent，能否在不重新建構同一份脈絡的情況下理解約束？

## 從親手執行工藝，到編碼工程判斷

Agent 時代之前的昂貴流程，訓練出一些有價值的直覺。開發者學會懷疑看似合理的輸出，跨越邊界追蹤行為，並驗證瀏覽器實際做了什麼。沒有理由為了保留這些經驗，而繼續保留意外教會它們的機械勞動。

不久之後，Agent 可能在人類解釋完篩選器行為之前，就完成實作。持續有價值的工作，是讓解釋足夠精確，為 Agent 提供有邊界的平台，並要求證據證明結果在真實系統裡成立。

前端開發並沒有消失。它的判斷正在從親手製作每個修改的人，轉移到讓大量修改值得信任的平台、契約與驗證循環中。
