假設代理提交一筆倉庫預留。服務已完成寫入，但回應遺失。代理看到逾時後建立另一個請求，於是同一個意圖產生兩筆預留。

錯誤假設是沒有回應就沒有副作用。增加代理的重試額度前，應先決定如何處理結果不明的寫入。這是面向 H1 2027 的工程措施提案，不是已執行的實驗或工作現場事故。

[Stripe 在 2017 年 2 月 22 日的工程文章](https://stripe.com/blog/idempotency)說明了服務完成操作、但回應未送達呼叫端的歧義。僅憑傳輸結果，無法判定業務結果。

## 讓多次嘗試沿用同一個操作身分

在假設的預留流程中，提交前先建立操作紀錄，包含已授權意圖、目的端、請求識別碼、參數與目前結果。重試歸屬於這筆紀錄。工作程序重啟時，應恢復紀錄，而不是因為本機記憶體空白就建立全新操作。

[AWS 的冪等 API 指引](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)區分呼叫端提供的請求身分與相同參數：外觀相同的兩個請求可能代表兩個不同意圖。去重需要服務契約；對任意端點加上一個標頭並不能建立保證。

最小而有用的審查，是在獲授權的測試環境注入一次失敗：讓預留完成寫入，抑制回應，再透過實際轉接器重試。同時檢查持久化結果與回傳訊息，要求原始意圖只對應一筆預留。這是建議的測試，不是已觀察的結果。

## 讀清楚端點的保證範圍

[Stripe 目前的 API 參考文件](https://docs.stripe.com/api/idempotent_requests)指出，API v1 會重播已儲存的回應，包括 500 錯誤；金鑰清除後再使用會建立新請求。API v2 的重試行為不同。不要把某個版本的契約套用到另一項服務。

對預留轉接器，記錄支援的重試期限及逾期後的處理方式。修改數量或目的端需要明確的新決定，不能成為自動規避先前錯誤的嘗試。新金鑰無法消除舊操作結果的不確定性。

## 停下時留下足夠的核對證據

如果端點沒有必要保證，或操作已超過有效期限，就暫停自動寫入。保留操作紀錄，透過獲授權的狀態查詢或人工核對處理。如果查詢可能延遲或未涵蓋相關範圍，查無結果仍不足以判定操作未發生。

交接應區分確認成功、確認拒絕及結果未知。重試次數與經過時間都應附屬於原始意圖。達到重試上限不能抹除不確定性，也不能把任務標示為完成。

這項措施需要持久化狀態、針對轉接器的測試，以及負責未決結果的人。它不會讓跨服務流程具備原子性，也不授權補償操作。先從一個重要的寫入邊界開始，不要承諾代理整條工具鏈都只執行一次。
