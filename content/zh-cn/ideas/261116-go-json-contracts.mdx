[11 月 4 日的 Go 公告](https://go.dev/blog/jsonv2)指出，`encoding/json/v2` 与 `encoding/json/jsontext` 已在 Go 1.27 成为稳定功能。这是审查 JSON 边界的好时机，却不是一次替换全部 import 的理由。本文提出审查计划，没有执行 Go 迁移或性能测试。

## 分开两项决策

[版本说明](https://go.dev/doc/go1.27#encodingjsonv2)指出，现有 `encoding/json` API 持续受到支持，并通过新实现保留行为，但错误文字可能不同。因此，工具链升级与采用 v2 语义需要分开的证据。

先记录每个边界实际使用的工具链、import 与选项。改 import 前先执行现有契约测试。如果测试比对完整错误文字，应判断文字究竟是公开契约，还是偶然的实现细节。不要为了让构建通过就删掉断言；若契约真正要求的是行为，就改成检查该行为。

## 分开测试输入接受与输出

[v2 参考文档](https://pkg.go.dev/encoding/json/v2)说明默认会拒绝重复的对象名称与无效 UTF-8。这些默认值值得用来重新检查过去接受的数据。同一套序列化程序生成数据后成功往返，不能取代其他生产端送入数据的边界测试。

准备小型合成数据集：一般请求、重复名称、格式错误的文字、大小写不同的字段名称，以及缺少、null 或空集合值。逐项记录预期接受结果与解码含义，再另外核对输出的 JSON 是否符合实际消费端的期待。测试数据不要包含个人信息、凭证或从生产环境复制的内容。

## 让例外可以审查

先迁移一个边界，并由能说明兼容需求的负责人参与。如果某个选项保留旧行为，就记录受影响的生产端、必要原因，以及移除条件。避免用全局兼容设置掩盖仍依赖旧行为的契约。

性能评估应另外进行：固定版本、输入形状与选项，再测量重要的工作负载。通过兼容测试不代表加速，也不代表普遍安全。实用的审查应留下明确的接受矩阵、消费端检查与回退决策，而不只是改过的 import 路径。
