[Python 3.15.0 于 2026 年 10 月 9 日成为稳定版本](https://www.python.org/downloads/release/python-3150/)，其中一项新增功能是显式延迟导入。本文评估它的工程取舍，不是即时发布新闻，也不是已完成迁移的记录。本文没有测量应用程序的加速幅度。

值得问的是初始化应该发生在哪里。命令行工具可能还不知道用户要生成报表还是查看帮助，就先导入成本很高的报表依赖。延后导入可能省去帮助路径上的工作，也会改变报表路径初始化依赖及发现错误的时间。

## 名称可以先绑定，模块稍后才加载

[Python 3.15 语言参考文档](https://docs.python.org/3.15/reference/simple_stmts.html#lazy) 说明了 `lazy import module` 与 `lazy from module import name`。它们先绑定延迟代理对象，在首次使用导入名称时才加载模块。`from` 导入在需要时仍会加载整个模块，不会只执行被请求的那个定义。

这个语法仅限模块作用域，不能放在函数、类主体或 `try`／`except`／`finally` 块内；星号导入与 future statements 也不能延迟。检查自动转换时，这些限制很重要：为每个 import 加上关键字并不是有效的迁移策略。

如果源码还必须让较旧的 Python 解析，文档提供 `__lazy_modules__`：在模块级列出完整模块名称的容器，让 3.15 将匹配名称的普通导入视为延迟导入。它保留旧语法，但仍需在每个支持的解释器上验证行为，不代表各版本的导入时机相同。

## 失败时机也是接口的一部分

文档指出，包括 `ImportError` 与 `SyntaxError` 在内的模块加载错误会在首次使用时发生。因此，成功导入应用程序的入口模块，不能证明所有延迟依赖都能加载。

以可选的导出命令为例，有用的验收测试会在缺少可选依赖的环境执行该命令，检查错误消息与退出状态。成功执行 `--help` 验证的是另一条路径，两者都重要，不能互相替代。

必须在启动时检测失败的地方，保留立即导入。如果有意延后加载，就在首次使用的边界检查错误处理。不要捕获所有异常，再一律声称缺少可选包：依赖自身的初始化也可能出错，过宽的回退处理会掩盖真正的缺陷。

这是建议的检查方法，本文并未在 Python 3.15 上执行这个示例。

## 注册可能就是导入原本在做的事

[PEP 810 的副作用说明](https://peps.python.org/pep-0810/#how-do-lazy-imports-affect-modules-with-import-time-side-effects) 指出，导入时的副作用也会延后，并建议使用显式初始化函数，避免依赖导入顺序。

这会影响只为了注册处理器而导入的插件模块。如果后续代码没有使用它的导入名称，预期触发注册的事件就可能永远不发生。其他测试如果先立即导入了插件，反而可能掩盖问题。

有限范围的采用应先找出这类导入。保留必要注册的立即执行，或加入显式初始化调用，并用全新进程测试。不要让启动性能补丁变成未经审查的插件发现机制重新设计。初始化顺序即使原本隐含在代码中，仍是应用程序行为。

## 测量真正支付成本的路径

比较立即导入与选定的延迟导入时，固定依赖版本与解释器配置。记录环境，重复测量全新进程；在已有进程中使用已加载的模块，回答的是不同问题。

| 路径 | 应保留的证据 |
| --- | --- |
| 帮助或其他轻量命令 | 生成有用输出的时间，以及是否需要重型依赖 |
| 首次使用依赖的命令 | 包含初始化的端到端延迟，以及命令的实际结果 |
| 缺少或损坏的依赖 | 诊断消息、退出状态，以及是否在预期边界失败 |
| 依赖注册的命令 | 不靠其他测试先导入，也能获得必要处理器 |

这些是建议的检查项，不是性能测试结果。即使完整命令没有变快，更快的帮助输出仍可能有价值；首次使用变慢，也可能不符合特定工作流的需求。应根据该流程的延迟预算判断，不能把延后工作当成消除工作。

先选择初始化契约已理解、且常用路径不需要的依赖。行为与测量结果支持后，再扩大范围。显式延迟导入让审查者看得到这个决定；真正要审查的是哪些事情现在可能晚一点发生。
