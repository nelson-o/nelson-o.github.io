[Vite 在 2026 年 6 月 23 日的 8.1 公告](https://vite.dev/blog/announcing-vite8-1)中介绍了实验性的 chunk import maps。本文依据 11 月 10 日查阅的官方文档，评估这项已有功能；不是新版本快讯，也没有声称实测性能提升。

真正值得回答的是：减少不必要的 chunk 变更，是否值得增加一项必须验证的发布行为？更新量变小固然有价值，但读者在部署前、部署中与部署后，都仍需加载一致且可运行的应用。

## 把 chunk 身份与当前 URL 分开

[Rolldown 文档](https://rolldown.rs/reference/InputOptions.experimental#chunkimportmap)说明了不依赖内容哈希的 chunk key。Import map 将这些 key 映射到生成的文件，减少仅因依赖文件名改变而造成的连带变更。

这个机制适合用一个明确的实验评估：只修改一个小型叶节点模块，再比较前后两次构建。哪些文件改变？压缩后的变更字节有多少？代表性路由实际会请求其中哪些文件？只计算改名文件数，可能夸大很小或根本不会在该路由加载的文件所带来的收益。

除了刻意修改的内容，固定源码版本、锁文件、构建配置与压缩设置；分别比较关闭与启用选项的结果。这是建议的测量方式，本文没有实际执行 Vite 构建实验。

## 保留实验功能的边界

当前的 [Vite 选项文档](https://vite.dev/config/build-options#build-chunkimportmap)将 `build.chunkImportMap` 标为实验性、默认关闭，且需要 `import.meta.resolve` 支持。因此，发布评审应列出实际支持的浏览器，不能把构建成功视为浏览器兼容性的证明。

[功能指南](https://vite.dev/guide/features#chunk-import-map-optimization)也指出，CSS 与资源不完全适用这项优化。修改资源仍可能使引用它的 chunk 改变，只是失效不一定继续传递给上层引用者。

这些限制适合用小范围试验处理，而不是一次应用到所有项目。比较时同时包含纯 JavaScript 修改与资源或样式修改。若平时发布的大部分变动来自图片与样式，JavaScript 的结果未必代表日常更新成本。

8.1 公告也提醒，当时 `experimental.renderBuiltUrl` 无法与此选项搭配。若交付流程依赖自定义 URL 改写，规划采用前应先验证评审中的确切版本是否支持这个组合。

## 把文档与它引用的文件视为同一次发布

有了映射表，不代表旧文档会自动变成新版本。已经打开的标签页仍可能需要原来版本的文件。因此，即使公开 URL 相同，新标签页与旧标签页也是不同测试场景。

Vite 的[生产构建指南](https://vite.dev/guide/build#load-error-handling)讨论了旧部署资源被删除后，动态导入可能失败，并建议以 `Cache-Control: no-cache` 让 HTML 重新验证。这是发布评审的背景，不代表一个缓存响应头就能解决所有旧标签页场景。

评估采用时，记录主机如何准备新文件、切换入口文档、保留旧文件，以及恢复前一版。检查该主机实际返回的响应头与资源行为；不要假设应用配置能控制 CDN。这是运维评审建议，不是修改本站的主机或安全配置。

可以用一个简短的验收表区分这些场景：

| 场景 | 建议保留的证据 |
| --- | --- |
| 更新后打开全新浏览器 | 入口文档、请求的 chunk URL 与成功呈现的路由 |
| 更新前已打开标签页，之后进入懒加载路由 | 旧引用仍能解析，或应用提供明确的恢复方式 |
| 发布期间仍使用缓存文档 | 在已说明的保留期内，其引用文件仍可获取 |
| 回滚版本 | 恢复的文档与必要文件组成可运行的前一版 |

旧标签页测试应包含真实合理的未完成操作。强制刷新让画面恢复正常，却丢失表单内容，与安全恢复不是相同结果。应明确决定这项行为，而不是把任何重新加载都当作成功。

## PR 需要两种证据

优化评审应同时包含缓存比较与发布一致性检查。记录确切 Vite 版本、选项值、受控的源码变更、压缩后的变更字节、浏览器覆盖范围，以及文件保留与回滚假设。把失败与尚未测试的组合和正面结果一起呈现。

Agent 可以协助收集这些产物，但 bundle 变小的描述，不能证明旧会话能跨越部署。让采用过程可回滚；若已证明的收益不值得兼容性与运维工作，就保持关闭。目标是减少不必要的传输，同时让发布行为仍能清楚说明。
