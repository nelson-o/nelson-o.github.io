假设代理提交一笔仓库预留。服务已完成写入，但响应丢失。代理看到超时后建立另一个请求，于是同一个意图产生两笔预留。

错误假设是没有响应就没有副作用。增加代理的重试额度前，应先决定如何处理结果不明的写入。这是面向 H1 2027 的工程措施提案，不是已执行的实验或工作现场事故。

[Stripe 在 2017 年 2 月 22 日的工程文章](https://stripe.com/blog/idempotency)说明了服务完成操作、但响应未送达调用端的歧义。仅凭传输结果，无法判定业务结果。

## 让多次尝试沿用同一个操作身份

在假设的预留流程中，提交前先建立操作记录，包含已授权意图、目标端、请求标识符、参数与当前结果。重试归属于这笔记录。工作进程重启时，应恢复记录，而不是因为本地内存为空就建立全新操作。

[AWS 的幂等 API 指引](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)区分调用端提供的请求身份与相同参数：外观相同的两个请求可能代表两个不同意图。去重需要服务契约；对任意端点加上一个请求头并不能建立保证。

最小而有用的审查，是在获授权的测试环境注入一次失败：让预留完成写入，抑制响应，再通过实际适配器重试。同时检查持久化结果与返回消息，要求原始意图只对应一笔预留。这是建议的测试，不是已观察的结果。

## 读清楚端点的保证范围

[Stripe 当前的 API 参考文档](https://docs.stripe.com/api/idempotent_requests)指出，API v1 会重放已存储的响应，包括 500 错误；密钥清除后再使用会建立新请求。API v2 的重试行为不同。不要把某个版本的契约套用到另一项服务。

对预留适配器，记录支持的重试期限及过期后的处理方式。修改数量或目标端需要明确的新决定，不能成为自动规避先前错误的尝试。新密钥无法消除旧操作结果的不确定性。

## 停下时留下足够的核对证据

如果端点没有必要保证，或操作已超过有效期限，就暂停自动写入。保留操作记录，通过获授权的状态查询或人工核对处理。如果查询可能延迟或未涵盖相关范围，查无结果仍不足以判定操作未发生。

交接应区分确认成功、确认拒绝及结果未知。重试次数与经过时间都应附属于原始意图。达到重试上限不能抹除不确定性，也不能把任务标示为完成。

这项措施需要持久化状态、针对适配器的测试，以及负责未决结果的人。它不会让跨服务流程具备原子性，也不授权补偿操作。先从一个重要的写入边界开始，不要承诺代理整条工具链都只执行一次。
