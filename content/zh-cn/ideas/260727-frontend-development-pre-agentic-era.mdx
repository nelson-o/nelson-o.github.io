## 添加一个筛选器

「添加一个筛选器」曾经是很常见的前端需求。这句话短得足以成为工单标题，最终看得见的结果，可能只占工具栏上的二十个像素。

这不是某个真实项目的完整复述，而是由许多前端代码库里反复出现的修改组合而成。那时，编码 Agent 还没有进入日常工作流。

第一个问题通常不是如何渲染控件，而是这个筛选器究竟代表什么。它应该包含哪些记录？是否和现有搜索组合？刷新后是否保留？状态要不要写入 URL？默认值由谁决定？API 很慢、结果为空，或者旧浏览器对输入控件的处理不同时，又该怎么办？

一个控件就可能暴露产品歧义、数据语义、交互设计、状态所有权和发布风险。代码只是整段工作里最看得见的中间部分。

## 交接链

在 Agent 时代之前，角色边界往往沿着实现工作堆积的位置形成。

设计师描述预期交互，前端开发者把它翻译成浏览器行为，后端开发者提供或修改查询契约。当两端无法对齐时，全栈开发者负责跨越缝隙。QA、审查者和发布负责人再确认这些部分能否整体成立。

这些边界很有用，但也形成了一条交接链。每个人都要重新构建同一个问题的不同部分。缺少 loading state，就退回设计；查询无法表达，就退回后端；测试发现不一致，就带着截图、payload 和复现步骤沿着链条往回走。

角色名称不只描述专业能力，也描述昂贵的人类工作会在哪里排队等待。

## 看不见的工作

修改组件之前，前端开发者必须先建立一个心智模型。

这意味着找到路由、追踪组件树、定位状态存储、阅读 API client、查看类似筛选器在其他地方如何工作，并从旧 pull request 里寻找从未进入文档的决策。还要比较设计稿和现有产品，判断哪一个才代表现实。

浏览器标签页变成工作记忆：框架文档、issue tracker、兼容性表格、network trace，以及只解决一半问题的示例。剩余的空白由对话填补。等真正开始实现时，困难工作大多已经发生，却很少出现在 diff 里。

组件渲染出来之后，循环还会继续。开发者尝试不同筛选组合、刷新页面、改变 viewport size、检查 request、修复测试、等待 CI、回应 review，再检查部署后的结果。「完成」不是代码已经存在，而是足够多的不确定性被消除，让修改值得信任。

## 平台工作早已不可缺少

团队无法只靠个人能力扩展这类工作。即使在 Agent 时代之前，前端平台投入也已经是必需品。

设计系统减少重复决策；组件库保存无障碍与交互行为；类型化 API client 让契约漂移可见；本地工具缩短反馈循环；预览环境让审查不再依赖每个人重现分支。CI、浏览器测试、视觉回归与可观测性，则把预期转化为可以重复执行的检查。

这些系统有时被视为功能交付之外的次要工作，但正是它们让功能交付可以持续。铺好的道路让开发者不必为每个需求重新构建按钮、表单、loading state、构建配置和测试设置。

平台主要放大人类的实现能力。收集上下文、选择路径、编写修改、解释检查结果，仍然由人完成。平台只是让这条手动循环更快、更一致。

## UI 构建不再稀缺

Agent 与 UI builder 改变了这条循环的经济性。

Agent 可以搜索仓库、找到类似筛选器、添加组件、更新状态、接入查询参数，并在一次处理中起草测试。它可以在团队过去完成第一个实现之前，就生成多个版本。曾经需要长时间机械专注的跨文件修改，现在变得廉价。

这不代表工作会自动正确。消失的是实现的稀缺性。产出一个看起来合理的界面，不再像过去那样是主要限制。

这个区别很重要，因为工程角色有一部分是围绕「谁能产出哪种成果」组织起来的。当产出变得廉价，前端、后端和全栈的旧边界就不再具有同样的解释力。更困难的边界会移向：谁定义约束，以及如何验证结果。

## 角色边界开始移动

专业分工不会消失，但重心会改变。

| 角色 | Agent 时代之前的中心 | Agent 时代带来的压力 |
| --- | --- | --- |
| 设计师 | 产出界面意图并交给实现 | 让状态、约束、token 与质量标准能被生成系统理解 |
| 前端开发者 | 实现面向浏览器的行为 | 塑造 UI 架构、平台规则与界面特有的验证方式 |
| 后端开发者 | 实现服务与数据契约 | 编码领域不变量、运行限制与契约，让生成的 client 无法轻易违反 |
| 全栈开发者 | 通过实现两端跨越边界 | 编排跨边界修改，并验证整合后的行为是否解决需求 |
| 平台开发者 | 加速人类开发者 | 约束、引导、观察并验证大量生成的修改 |

决定层级、交互、无障碍和产品语言时，设计师的专业能力仍然重要。前端专家仍然理解浏览器、渲染、性能与交互状态的失败模式。后端专家仍然负责领域行为、安全、数据完整性与运行后果。全栈工程师仍然能看见任何单侧视角都会遗漏的整合缺口。

真正改变的是，各角色需要亲手构建多少内容，才能表达自己的专业判断。工作可以从产出一个实现，转向定义一个能够安全产出许多实现的系统。

## 平台成为控制平面

在 Agent 工作流里，前端平台不再只是生产力层，而会成为控制平面。

设计 token 缩小视觉选择范围；组件 API 提供认可的交互模式；schema 定义有效的数据形状；仓库指令公开本地约束；标准示例展示预期架构；测试 fixture 让边界情况可以复现；CI 政策决定一项修改继续前进之前必须提供哪些证据。

Agent 能沿着明确路径快速前进，是因为这条路径承载了人类之前编码进去的判断。没有这条路径，速度只会带来局部发明：几乎相同的组件、不一致的状态模型、无法审查的 diff，以及只能证明生成实现与自身一致的测试。

这也改变了平台工作的价值。一次平台改进，不再只是为每个记得使用它的开发者节省几分钟；它可以塑造进入仓库的每一个生成修改。杠杆更大，但糟糕默认值的代价也更大。

## 更少的人类实现，更多工程化验证

如果 Agent 用更少的人类工作产出更多修改，验证就不能继续停留在最后的手动作业。人类的审查注意力，无法和生成输出以同样速度扩展。

解决方式不是要求开发者审查更多代码，而是工程化更强的证据：

- 验证前端与后端假设的契约测试
- 发现布局与设计系统漂移的视觉回归
- 检查语义与交互的无障碍测试
- 覆盖用户可见流程的端到端测试
- 支持真实检查的预览环境
- 观察只在发布后出现行为的可观测性
- 限制风险的 scoped diff、发布控制与回滚路径

这些检查本身就是开发工作。它们需要和过去功能实现同样的谨慎：判断什么重要、建模失败、选择有效边界，并保持信号可靠。

检查也不是越多越好。生成的修改可以在解决错误问题的同时通过浅层测试。庞大的测试套件也可能变得缓慢或嘈杂，最终失去信任。哪些属性必须是不变量、哪些结果需要观察、哪些例外值得投入注意力，仍然需要人类决定。

有价值的转变，是从反复检查每个机械步骤，转向把规则编码一次，再持续应用。

## 新的稀缺工作

问题定义仍然是人类工作，但它只是新角色的一部分。更大的机会，是让工程判断可以重复利用。

这包括在生成之前解决歧义，强化团队反复产生分歧的契约，以平台原语取代又一个一次性组件，并在缺陷逃逸后改进验证。它也包括处理例外：陌生风险、冲突约束、生产事件，以及现有控制平面无法给出可信答案的修改。

前端开发者面对的问题，会比「我能否构建这个界面？」更广：系统是否让预期界面容易生成？是否让错误界面难以发布？其他开发者、设计师、后端工程师或 Agent，能否在不重新构建同一份上下文的情况下理解约束？

## 从亲手执行工艺，到编码工程判断

Agent 时代之前的昂贵流程，训练出一些有价值的直觉。开发者学会怀疑看似合理的输出，跨越边界追踪行为，并验证浏览器实际做了什么。没有理由为了保留这些经验，而继续保留意外教会它们的机械劳动。

不久之后，Agent 可能在人类解释完筛选器行为之前，就完成实现。持续有价值的工作，是让解释足够精确，为 Agent 提供有边界的平台，并要求证据证明结果在真实系统里成立。

前端开发并没有消失。它的判断正在从亲手制作每个修改的人，转移到让大量修改值得信任的平台、契约与验证循环中。
