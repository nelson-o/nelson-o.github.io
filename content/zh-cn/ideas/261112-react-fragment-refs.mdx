[2026 年 9 月 9 日发布的 React 19.3](https://react.dev/blog/2026/09/09/react-19-3)将 Fragment refs 列为稳定功能，让程序在不增加 DOM 包装元素的情况下进行命令式操作。本文是 11 月 12 日对已有功能的评估，不是新版本快讯，也不是已执行的迁移报告。

如果容器只是为了放置 ref 而新增，它可能适合移除。但若容器承担有用的布局或语义责任，就需要另一种判断。审查应从元素的工作开始，而不是从能删除多少元素开始。

## 把操作接口与容器分开思考

假设一个结果组件会返回标题与数个控件。父层可能需要把焦点移入结果，同时又希望子元素直接参与外层布局。这是值得评估 Fragment ref 的场景。

修改前，列出现有容器承担的责任：CSS 选择器、定位假设、事件处理器、无障碍名称及测试定位方式。决定哪些责任可以消失，哪些仍需要实际元素。命令式操作接口本身不能取代标题、具名区域或表单分组。

保留承载预期意义的标记。如果问题只是组件 API 不方便，应比较“让组件公开一个有限的动作”与“让调用方操作较大的群组”。减少包装元素，不应悄悄扩大责任范围。

ref 必须使用明确的 `<Fragment ref={...}>` 语法，不能使用 `<>`；取得的操作对象是 `FragmentInstance`，不是 `HTMLElement`。详见 [API 参考文档](https://react.dev/reference/react/Fragment)。

## 焦点目标是产品决策

[Fragment 参考文档](https://react.dev/reference/react/Fragment)指出，`focus()` 会以深度优先方式搜索嵌套子元素中的第一个可聚焦节点；事件监听与观察器则针对第一层 DOM 子元素。

在结果组件中，“聚焦结果”究竟是什么意思？是主要动作、失败后的重试按钮，还是加载完成才出现的控件？只有当所有相关状态的目标都符合意图时，通用群组操作才有帮助。

可规划一个含两个控件的测试，再把新控件插入前方。接着测试第一个控件禁用、结果为空，以及条件式错误动作。记录用户触发操作后实际取得焦点的元素，也检查一般 Tab 导航：命令式移动成功，无法证明其余键盘路径合理。

如果不论子元素顺序如何，都必须聚焦特定动作，就应把目标写入组件契约。不要让偶然的源码顺序变成后续贡献者不知道的限制。

## 分别审查事件与观察

不要把“群组的 ref”理解为“一个普通容器元素”。对事件集成，记录处理器对 target 的假设、传播方式，以及哪一层负责注册与清理。在替换旧容器上的监听器前，先比对所选 API 是否符合这些预期。

对观察器集成，决定应用程序需要整个区域的一个结果，还是个别成员的观察结果。写清楚这些结果如何转换成加载内容或更新可见状态等产品决策。汇总规则应明确设计，不该因为简单演示中回调恰好执行一次，就自行推定。

测试挂载、增删子元素及卸载群组，并加入重复循环，让重复注册或过期观察可以被看见。这些是建议检查项目，不是本文已完成的 Fragment-ref 实验结果。

## 用不同证据审查同一个改动

| 关注点 | 建议的前后比较证据 |
| --- | --- |
| 布局 | 相同外层 grid 或 flex 布局、窄视口与长内容 |
| 意义 | 预期的标题、名称与分组仍然存在 |
| 焦点 | 加载、错误、空结果及重新排序状态中的指定目标 |
| 事件与观察 | 重复变动时，回调、汇总与清理符合预期 |

截图可以呈现移除容器是否改变布局；键盘操作记录可以呈现焦点去了哪里。两者无法互相证明。除了这些证据，也应检查最终 DOM 与相关无障碍信息，并在审查中保留失败结果。

采用决策应记录确切的 React 与集成版本，并保留小范围回退方式。本文没有执行依赖升级、性能测试或无障碍审计。值得追求的是更清楚的组件契约，并保留必要标记，而不是全面把容器换成 Fragment。
