Node.js 26 在 **2026 年 10 月 28 日，以 26.13.0、代号 Lithium 进入 LTS**。[官方发布公告](https://nodejs.org/en/blog/release/v26.13.0) 说明，这个版本调整了 LTS 元数据，其余内容与 26.12.1 相同，计划持续提供更新至 2029 年 4 月。

评审升级时，这个区别很重要。进入 LTS 改变的是维护周期，并不意味着运行环境可以直接沿用较早主版本的假设。

同一份公告指出一个具体边界：**官方 Linux 二进制文件从 Node.js 25 起便链接 libatomic**。从较早 LTS 升级的团队，可能需要在 Linux 环境补上这个运行时库。包锁定文件无法证明它已经存在。

本文分析这次发布，并提出升级评审顺序；并未实际完成 Node.js 26 迁移、观察到生产环境故障，或进行性能测试。上述版本号用于识别公告，不是建议把部署永久固定在这个补丁版本。

## 一起评审可执行文件与环境

[固定在该版本的构建文档](https://github.com/nodejs/node/blob/v26.13.0/BUILDING.md#official-binary-platforms-and-toolchains) 明确指出：官方 Linux 二进制文件运行时，必须能够找到 libatomic。根据发行版不同，包名通常是 `libatomic` 或 `libatomic1`。文档也区分了支持平台与生成官方二进制文件所用的工具链。

因此，应用团队的评审范围，不应只有 `engines.node` 或 CI 的版本选项。应记录实际运行应用的 runtime 产物、CPU 架构、基础镜像，以及操作系统包。

设想一个多阶段镜像：在工具齐全的构建环境成功编译后，把 Node 复制到更精简的运行镜像。构建成功只证明了构建环境的某些条件，不能证明最终镜像具备启动该可执行文件所需的库。这是一种假设的失败模式，不是声称某个特定镜像存在问题。

应优先取得最终产物的证据。在把应用测试当成第一个诊断工具之前，先在预定的运行镜像与发布架构内，进行最小启动检查。

## 分别检查启动、依赖加载与行为

实用的评审顺序可以分成三道检查：

| 检查 | 问题 | 保留的证据 |
| --- | --- | --- |
| Runtime 启动 | 选定的可执行文件能否在最终环境启动？ | 精确版本、镜像标识、架构与命令结果 |
| 依赖加载 | 应用实际安装的依赖能否加载？ | 确实使用原生依赖的 import 或启动检查 |
| 应用行为 | 应用是否仍符合既定契约？ | 相关集成测试、构建／导出检查与上线观察 |

这个顺序能缩小调查范围。进程无法启动时，不该先把问题当成框架退化。原生扩展加载失败，也不该被模拟该边界的单元测试掩盖。即使 import 成功，仍无法充分说明应用在负载下的行为。

对于静态前端，相关的 Node 环境可能是构建 runner，而不是托管平台。应检查生成导出文件的环境；如果应用还有 Node 服务器，也要检查部署后的运行环境。相同的主版本标签，可能掩盖这两条路径上的环境差异。

代价是额外的 CI 工作。让启动检查保持精简，把昂贵的行为测试放在应用真正会遇到的环境。针对实际交付的架构与镜像变体建立小型矩阵，比测试所有可获取的镜像更有用。

## 原生扩展还有另一道兼容性边界

Node-API 在这里很有帮助，但它的保证有适用范围。[Node.js 26.13.0 的 Node-API 文档](https://nodejs.org/docs/v26.13.0/api/n-api.html#implications-of-abi-stability) 描述了 Node-API 的 ABI 稳定性，也提醒其他 Node.js API 与扩展使用的外部库，不一定具有相同保证。

不要把评审简化成“这个包使用了 Node-API，所以升级没问题”。应确认安装程序选中了哪个二进制文件、它针对哪个平台，以及需要哪些外部库。如果依赖使用其他原生 API，就要检查它自己的兼容性政策，不能直接套用 Node-API 的承诺。

这对由 agent 准备的升级也很重要。纯 JavaScript 测试通过，是那些测试的有效证据，却不是最终镜像成功加载原生依赖的证据。应要求 agent 说明实际测到了哪个边界、保留命令结果，而不是只提供笼统的兼容性结论。

## 让回滚方案指向完整产物

有用的升级 PR 会列出新旧 runtime／镜像组合、分别运行过的检查，以及可以恢复的发布产物。如果基础镜像或操作系统包也变了，只回滚版本选项并不足以明确界定回滚结果。

这不意味着所有变量都要一起修改。只要组合受到支持，评估 runtime 时固定基础镜像，可以让故障更容易定位。如果镜像也必须更新，就把这个依赖关系写清楚，并测试最终组合。

LTS 里程碑的实际价值，是让支持规划与兼容性验证一起进行。这次发布的 libatomic 提醒，具体指出 runtime 契约不只包含 JavaScript 源码与包依赖图，也包含启动可执行文件的环境。
