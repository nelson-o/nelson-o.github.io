## 添加一个筛选器

“添加一个筛选器”听起来仍是很小的前端需求。它短得足以放进工单标题，画面上可能只多出工具栏里二十个像素的控件。

但这项需求要从产品问题开始。哪些用户需要它？要包含哪些数据？默认值是什么？是否要和搜索条件一起使用？团队如何确认它真的有帮助？

产品经理要把这些问题整理成用户目标、验收条件、数据指标和 rollout 计划。设计也不能只画正常流程，还要定义空白、加载、错误和窄屏状态。

工程端接着要决定筛选条件该放在 URL、本地状态，还是共享状态库。API 可能需要新增查询参数、更新 schema、处理分页，并清楚响应没有匹配记录的情况。

组件只是整项修改的一部分。测试、遥测数据、功能开关、发布说明和回滚路径可能同样重要。

这不是站在未来回顾转型的故事，而是 agentic engineering 刚起步的现场：Agent 已经进入交付流程，团队却还在摸索这套流程该如何运作。

## Agent 已经改变了什么

Agent 可以搜索代码仓库、找到类似的筛选器、追查组件与 API 客户端、修改多个文件，再起草测试。以前开发者可能还在收集上下文，它已经交出第一版代码差异。

这种速度已经改变日常工作。开发者可以先让 Agent 实现，检查代码差异，指出遗漏的状态，再要求它缩小修改，不必亲手输入每一行代码。

产品和设计也能更早验证想法。可操作的预览版本会在完整开发之前，暴露不清楚的默认值、遗漏的权限规则，或难用的移动端交互。

但输出得快，不代表需求已经解决。Agent 可能复制已有错误、选错抽象层、用自己的假设编写测试，或做出局部正确、整体却破坏其他流程的修改。

新能力已经出现，配套的工作方式却还没有成熟。

## 日常流程正在重建

好用的 Agent 工作流从提示词之前就开始。团队要先写清楚这次修改的用户目标、影响范围、预期状态、API 行为、不处理的事项，以及发布前必须提供的证据。

Agent 收到的应该是范围清楚的任务和代码仓库规范。它要交付可审查的代码差异，而不是在同一个 PR 里重做组件系统、更换依赖包，再改写无关测试。

开发者要同时审查设计与实现。URL 还能分享吗？服务端分页保留了吗？组件使用了现有设计系统吗？权限由后端执行，还是只在 UI 隐藏？

自动化检查要提供明确证据。契约测试验证请求与响应的假设；组件与无障碍测试验证各种状态和键盘操作；端到端测试覆盖用户可见的流程。

预览环境让产品、设计与工程查看同一个版本。功能开关控制开放范围，遥测数据反映使用情况和错误，回滚路径则处理生产环境与测试环境不同的意外。

上线后的信息要回到下一轮。遗漏的边界情况应该变成更清楚的验收条件、测试样例、组件 API 或代码仓库指引。

## 分工改变，责任没有消失

Agent 工程实践不会取消专业责任，而是改变各个角色投入注意力的位置，以及决策如何进入实现。

| 角色 | 新流程中的具体责任 |
| --- | --- |
| 产品经理 | 定义用户目标、优先级、验收条件、成功指标、rollout 与后续决策 |
| 设计师 | 定义交互状态、无障碍行为、响应式规则与产品用语 |
| 前端工程师 | 负责浏览器行为、状态、渲染、性能、设计系统用法与 UI 验证 |
| 后端工程师 | 负责领域规则、授权、数据完整性、API 契约与运行限制 |
| 全栈工程师 | 沿着 UI、服务、数据、测试与发布流程追查完整需求 |
| 平台工程师 | 维护组件 API、类型化客户端、代码仓库指引、CI、预览环境与可观测性 |

这些责任会在交付过程中重叠。产品决策会影响 API 形状，后端限制会影响交互设计，而前端错误状态可能暴露服务契约无法区分“没有结果”和“请求失败”。

Agent 可以跨文件带着这些信息工作，却不能默默替团队选择要承担哪一种取舍。这类决策仍要有清楚的负责人和可追溯的记录。

## 防护机制也是功能交付的一部分

团队常把平台工作和功能交付分开看待。当 Agent 参与开发，两者的关系就更难忽略。

定义清楚的组件 API，可以避免再做一个几乎相同的筛选器。自动生成的客户端让 UI 代码跟上服务 schema。测试样例则能重现权限过期，或分页后出现空页的情况。

代码仓库规范告诉 Agent 必须遵循哪些模式。CI 阻止类型错误、契约漂移、无障碍回归和失败的静态导出。预览环境则让审查者直接看到这次修改。

可观测性补上合并前测试看不到的部分，例如真实数据的延迟、特定浏览器错误、异常的空结果，以及用户到底有没有使用这个筛选器。

防护机制也要符合风险。低风险的文案修改，不需要和新查询路径一样多的证据。嘈杂的测试和模糊的指令都会拖慢人和 Agent，因此同样需要维护。

实际目标很简单：让预期的实现容易找到，让高风险的实现容易被发现，也让发布容易回滚。

## 我们已经一脚踏进新流程

大多数团队不会从全手动流程，一步跳进成熟的新模式。他们正在同一个迭代里混用新旧工作方式。

一张工单可能由人亲手完成，下一张从 Agent 生成的代码差异开始，第三张则只用 Agent 追查陌生的数据流或复现缺陷。

范围仍在变化。团队正在学习任务要附上多少上下文、生成的修改应该多小、人该在什么时候介入，以及哪些检查能提供证据，而不只是增加仪式。

日常习惯也在改变。规划开始包含给机器的指令，审查要追问生成的抽象设计，复盘则能把漏到生产环境的缺陷变成更好的测试样例、契约和代码仓库规则。

前端开发仍是浏览器、API、状态、测试与发布里的具体工作。产品管理仍要具体处理目标、优先级、验收条件与上线后的学习。

Agent 工程实践把这些决策接到更快的实现上。我们已经踏进这条路，却仍在一边前进，一边铺好脚下的路。
