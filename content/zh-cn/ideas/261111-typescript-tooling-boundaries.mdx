[2026 年 10 月 20 日公告](https://devblogs.microsoft.com/typescript/announcing-typescript-7-1-beta/)介绍了 TypeScript 7.1 beta 与预览版 API。[官方首页](https://www.typescriptlang.org/)在 11 月 11 日仍将 7.1 列为 beta。本文提出评估方法，没有执行迁移或性能测试。

命令行类型检查成功，只回答了那个命令能否检查那个项目。它无法证明自制文档生成器、lint 集成或编辑器辅助工具仍然理解同一个项目。这些集成是不同的使用方，各有输入与输出，应分别验收。

## 先盘点使用方，再调整包

[7 月 8 日的 TypeScript 7.0 发布公告](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)说明，7.0 没有编程 API，并为现有工具介绍了 TypeScript 6 兼容包。因此，较新的编译器可执行文件与较旧的 API 使用方，可以是刻意保留的工具链组合。

从实际依赖图与脚本开始，为每个使用方记录解析到的编译器包、使用可执行文件还是 API、配置来源，以及输出产物。不要假设更改顶层依赖，就会按预期更新工具内部的依赖或 peer resolution。

盘点表要足够精简，让人能审查。“文档生成器及其声明文件输出”是有用的一行；只有“支持 TypeScript”则不足以判断。移除可运行的兼容路径前，先确认各集成维护者明确支持的版本范围。

## 明确指定配置的责任归属

Beta 公告的 API 编译示例接收明确的文件与选项，不会加载 `tsconfig.json`。把示例带入项目工具时，还需要决定配置如何取得。

评估集成时，选择刻意限定的输入契约，或沿用项目现有的配置语义，再测试这项选择。案例应包含继承配置、预期根目录以外的文件，以及只在构建期间存在的生成式声明文件。先比较实际输入与选项，再比较诊断数量。

这对自动审查尤其重要：检查错误文件集合却显示绿灯，比清楚失败更容易误导。让命令输出足以识别配置与源码版本的非敏感信息，但不要把源码全文或环境变量倾倒进报告。

## 让失败与清理可以被观察

Beta API 要求释放 API 与 program 资源。长时间运行的集成应把资源归属视为正确性的一部分。

可以规划一个小型重复工作测试：打开项目、取得结果、结束请求，再重复执行。在成功案例之间加入失败与中断，确认后续工作仍能完成，每条退出路径都有清理。如果要评估资源滞留，应观察整段流程的进程内存；启动后的一次低用量读数，无法证明资源已释放。

另外决定诊断结果属于哪次请求。如果另一次编辑已使请求过时，调用方不应把旧结果当作最新答案。给请求加上源码版本或代次标识符，测试完成顺序颠倒的场景。这是集成设计建议，不代表 TypeScript 会自动替工具实现这个策略。

## 订出可回退的验收决策

| 审查项目 | 建议证据 |
| --- | --- |
| 输入 | 解析到的包、配置、根文件与生成式文件假设 |
| 输出 | 预期诊断、源码位置，以及适用时的输出产物 |
| 重复工作 | 成功、失败与中断请求之后，仍可成功处理新请求 |
| 回退 | 旧 lockfile 与使用方实现仍能重现已接受的结果 |

先比对正确性，再计时。若性能是评估目标，记录确切预发布版本、机器限制、源码版本、缓存状态与工作负载。单次检查应与重复的编辑器或服务请求分开。厂商公布的加速数字不是这个集成的测量，本文也不主张任何加速成果。

保留现有工具，同时以小范围 fixture 评估 beta，也可以是合理结论。逐项记录哪个使用方通过、失败或尚未测试。采用前重新确认发布状态与集成支持；预览 API 适合可回退的试验，不足以宣称所有依赖工具都已完成迁移。
