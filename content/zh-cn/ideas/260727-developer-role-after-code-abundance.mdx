我不再认为 agent 时代最核心的问题，是它们能不能写出有用的代码。它们能。

真正困难的是：当产出一个看似合理的实现，比判断它是否值得留在系统里还便宜时，我们该怎样工作？

## 瓶颈已经转移

过去，工程师有很大一部分时间花在把意图变成可运行的变更。agent 压缩了这段循环。

它们能探索 repository、起草实现，再根据反馈快速修正。变化的不只是输入代码的速度，也是变更交付给团队的速度。

当代码变得充裕，控制复杂度才成为工程工作。

稀缺的资源变成判断力：该改什么、哪些地方必须保持稳定，以及 pull request 不再新鲜后，系统还能承受什么。

## 代码的重要性正在改变

代码仍然是人需要理解的产物，但它也越来越是机器必须能安全检查、修改、测试和恢复的基础。

因此，明确的边界、可预测的结构、局部变更、可执行的检查、repository-native 的上下文，以及清晰的所有权和回滚路径，都更有价值。

人类可读性没有变得可有可无；它成为更广泛要求的一部分：代码库必须能由人治理，也能让机器安全运行。

如果 agent 能改一个系统、团队却说不清它如何运作，那不是适应力，而只是移动得很快。

## 便宜的代码可能带来昂贵的复杂度

agent 降低了新增代码的成本，却没有降低长期拥有它的代价。

一个看似合理的实现，仍可能引入不需要的抽象、重复已有概念、扩大变更范围，或遮蔽未来维护者和 agent 都必须重新理解的意图。

生成成本趋近于零；所有权成本却不会随之下降。

所以，生成的 slop 不只是美观问题。每一层没有理由的复杂度，都会多出一条要学的规则、一个要测试的分支，以及未来变更可能意外失败的位置。

代码出现得越快，我们越要谨慎决定哪些复杂度可以留下。

## 通过检查不代表变更足够好

validation 与 verification 提供不可或缺的证据：预期行为、类型一致性、构建兼容性，以及已知不变量是否成立。

但它们无法判断抽象是否必要、变更是否大得没有必要，或代码是否已经是最清楚的表达。

verification 问的是变更能不能工作；review 问的是这是不是我们应该拥有的变更。

机械检查应该尽早且频繁地运行；成功不等于可以跳过定性的 review。

这不是不信任自动化，而是让自动化承担它真正能做的工作，同时保留可见的设计判断。

## 开发者成为质量关卡

把这种转变简化成“开发者是 agent 的协调者”太浅了。

开发者要定义意图和约束、拆解工作、界定 agent 的任务范围、review 并修正实现、编写 guardrail 和验收标准，并承担 production 的后果。

这是一个在每个边界都主动介入的角色。好的 prompt 可以开始工作，但不能代替拒绝薄弱设计、缩小 diff、移除抽象，以及要求提供与风险相称的证据等判断。

## Agentic 开发的分阶段关卡

能让 agent 的速度保持有用的 workflow，需要一连串明确关卡：

```text
意图
  -> 设计关卡
  -> 范围受限的 agent 任务
  -> 小而可 review 的变更
  -> 人工 review 与修正
  -> validation 与 verification
  -> merge
  -> production 反馈
```

顺序很重要。低成本检查可以在整个循环中运行，但最终的 validation 与 verification 要在审慎的人类 review 和修正之后。

review 反馈可以把工作送回 agent；production 证据则应强化下一次的设计关卡和任务边界。

这不是瀑布式流程，而是一个让速度仍与所有权相连的受控循环。

## 在 slop 变成架构之前挡住它

最有效的 guardrail，是在生成结果固化为默认做法之前，就把日常的工程纪律落实到流程中。大量生成前先要求设计或变更契约。

拒绝过大或范围不清的 pull request；设定文件、dependency 与架构边界；宁可拆成几个脉络清晰的小变更，也不要一次塞进包罗万象的大改动。

要求 agent 回应 review 反馈并简化输出，而不是只再叠上一层 patch。把无法解释的复杂度视为需求没有达成。

merge 之前，要求与风险相称的证据：并非每个变更都需要同样的证明，但每个变更都要能说明为何应该进入 `main`。

## Senior developer 与 engineering lead 的工作如何改变

对 senior developer 而言，花在写出第一版实现的时间可能变少，花在塑造边界、追问抽象、修正输出，以及改善让人和 agent 都能安全修改的系统接口上的时间则变多。

工作更偏向架构，但不会因此脱离实现。

对 engineering lead 而言，交付系统必须避免生成速度超过 review 能力。团队应衡量的是已经 review、已经 verification、可维护的结果，而不是生成行数、agent 执行次数或 pull request 数量。

review 与修正的容量，本来就是系统真正的产能。

## 工程杠杆的新定义

最强的 agentic 工程师，不是产出最多代码的人，而是能把机器速度转成可维护变更、又不让复杂度悄悄累积的人。

工程杠杆，是预防、塑造并安全拥有复杂度的能力，而不是生成代码的数量。
