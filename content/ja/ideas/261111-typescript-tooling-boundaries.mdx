[2026 年 10 月 20 日の発表](https://devblogs.microsoft.com/typescript/announcing-typescript-7-1-beta/)では、TypeScript 7.1 beta とプレビュー API が紹介された。[公式サイト](https://www.typescriptlang.org/)でも 11 月 11 日時点で 7.1 は beta とされている。本稿は評価計画であり、移行やベンチマークを実施した報告ではない。

コマンドラインの型チェックが成功しても、確認できるのは、そのコマンドでそのプロジェクトを検査できたことだけだ。独自のドキュメント生成器、lint 連携、エディター補助ツールが同じプロジェクトを理解しているとは限らない。それぞれを入力と出力の異なる利用側として検証したい。

## パッケージを変える前に利用側を把握する

[7 月 8 日の TypeScript 7.0 発表](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)は、7.0 にプログラムから使う API が含まれないことを説明し、既存ツール向けに TypeScript 6 互換パッケージを紹介している。新しいコンパイラー実行ファイルと古い API 利用側を組み合わせる構成には、意図があり得る。

実際の依存関係とスクリプトから調べる。利用側ごとに、解決されたコンパイラーパッケージ、実行ファイルと API のどちらを使うか、設定の出所、生成物を記録する。最上位の依存を変えれば、ツール内部の依存や peer resolution も期待どおり変わるとは考えない。

一覧はレビューできる程度に小さく保つ。「ドキュメント生成器とその宣言ファイル出力」は有用な一行だが、「TypeScript 対応」だけでは判断できない。動作中の互換経路を外す前に、各ツールの保守側が明示する対応バージョンを確認する。

## 設定を誰が扱うか決める

Beta 発表の API コンパイル例は明示的なファイルとオプションを受け取り、`tsconfig.json` を読み込まない。例をプロジェクトのツールへ持ち込むなら、設定の扱いを別途決める必要がある。

評価では、意図的に限定した入力契約か、既存プロジェクトの設定の意味を保つ方式かを選び、その選択をテストする。継承した設定、想定するルートの外にあるファイル、ビルド中だけ存在する生成済み宣言ファイルを含めたい。診断件数を比較する前に、実際の入力とオプションを比較する。

自動レビューでは特に重要だ。誤ったファイル集合を検査して緑になるより、明示的な失敗のほうが判断しやすい。使った設定とソースのリビジョンが分かる非機密の情報を出力する一方、ソース全文や環境変数をレポートへ流し込まない。

## 失敗と解放を観察できるようにする

Beta API では API と program のリソース解放が必要になる。長時間動く連携では、リソースの所有を正しさの一部として扱う。

小さな反復テストを計画できる。プロジェクトを開き、結果を取得し、要求を終え、もう一度実行する。成功の間に失敗と中断を挟み、その後の処理が完了し、すべての終了経路で解放されるか確認する。保持されたリソースを評価するなら、処理全体でプロセスメモリーを観測する。起動直後の一度の低い値では、解放された証拠にならない。

診断結果がどの要求に属するかも決める。次の編集で要求が古くなった場合、呼び出し側は古い結果を最新として公開すべきではない。ソースのリビジョンや世代 ID を要求に付け、完了順が逆転するケースを試す。これは連携設計の提案であり、TypeScript がその方針を自動実装するという意味ではない。

## 戻せる受け入れ判断にする

| 確認対象 | 提案する証拠 |
| --- | --- |
| 入力 | 解決されたパッケージ、設定、ルートファイル、生成ファイルの前提 |
| 出力 | 期待する診断、ソース位置、必要に応じて生成物 |
| 反復処理 | 成功、失敗、中断の後も新しい要求が成功すること |
| ロールバック | 元の lockfile と利用側実装で、合意した結果を再現できること |

計時より先に正しさを比較する。性能も評価するなら、正確なプレリリース版、マシンの制約、ソースのリビジョン、キャッシュ状態、ワークロードを記録する。単発チェックとエディターやサービスの反復要求は分ける。ベンダー公表の高速化は、この連携での測定値ではなく、本稿も高速化の成果を主張しない。

既存ツールを維持し、限定した fixture で beta を評価する結論も妥当だ。利用側ごとに成功、失敗、未検証を記録する。採用前にはリリース状況と連携の対応を再確認したい。プレビュー API は戻せる試行の理由であり、依存するすべてのツールが移行済みだと述べる根拠にはならない。
