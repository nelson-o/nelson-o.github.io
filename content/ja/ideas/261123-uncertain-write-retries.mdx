仮に、エージェントが倉庫の引き当てを要求したとする。サービスは書き込みを完了したが、応答が失われた。エージェントはタイムアウトを見て別のリクエストを作り、一つの意図に対して二件の引き当てが生じた。

誤った前提は、応答がなければ副作用もないということだ。再試行の許容量を増やす前に、結果が不明な書き込みをどう扱うか決めたい。これは H1 2027 に向けた工学的な備えの提案であり、実行済みの実験や職場での事故ではない。

[Stripe の 2017 年 2 月 22 日の技術記事](https://stripe.com/blog/idempotency)は、サーバーが操作を完了しても応答が呼び出し元に届かない場合の曖昧さを説明している。通信の結果だけでは、業務上の結果は判断できない。

## 複数の試行で同じ操作を識別する

仮の引き当て処理では、送信前に操作記録を作る。承認された意図、送信先、リクエスト識別子、パラメーター、現在の結果を含める。再試行はその記録に属する。ワーカーが再起動したら、メモリーが空だからと新しい操作を作らず、記録を復元する。

[AWS の冪等 API の指針](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)は、呼び出し元が与える識別子と同一パラメーターを区別する。同じ形の二つの要求でも、意図は別かもしれない。重複排除にはサービスの契約が必要であり、任意のエンドポイントにヘッダーを加えても保証にはならない。

最小限の有用なレビューは、許可されたテスト環境で一つの障害を注入することだ。引き当てを確定させ、応答を抑止し、実際のアダプターから再試行する。返却メッセージに加えて永続化された結果も確認し、元の意図に対する引き当てが一件であることを要求する。これはテスト案であり、観測済みの結果ではない。

## エンドポイントの保証範囲を読む

[Stripe の現行 API リファレンス](https://docs.stripe.com/api/idempotent_requests)によると、API v1 は 500 エラーを含む保存済み応答を再生し、キー削除後の再利用は新しい要求になる。API v2 の再試行動作は異なる。あるバージョンの契約を別サービスに一般化してはいけない。

引き当てアダプターでは、対応する再試行期間と期限後の扱いを記録する。数量や送信先を変えるには明示的な新しい判断が必要であり、以前のエラーを自動的に回避する試行にしてはいけない。新しいキーは、古い操作の不確実性を解消しない。

## 停止時に照合できる証拠を残す

必要な保証がない、または操作がその有効期間を超えたなら、自動書き込みを停止する。操作記録を保持し、許可された状態照会や人による照合を行う。照会に遅延があり得る、あるいは対象範囲が不足するなら、検索結果がないだけでは未実行と判断できない。

引き継ぎでは、成功確認済み、拒否確認済み、結果不明を区別する。再試行回数と経過時間は元の意図に結び付ける。上限への到達によって不確実性を消したり、完了扱いにしたりしてはいけない。

この備えには永続状態、アダプター固有のテスト、未解決の結果を担当する人が必要だ。複数サービスの処理を原子的にするものでも、補償操作を許可するものでもない。重要な書き込み境界を一つ選んで始め、エージェントのツールチェーン全体で一度だけ実行されるとは約束しない。
