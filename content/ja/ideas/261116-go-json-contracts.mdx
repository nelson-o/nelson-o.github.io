[11 月 4 日の Go の発表](https://go.dev/blog/jsonv2)は、`encoding/json/v2` と `encoding/json/jsontext` が Go 1.27 で安定版になったと説明している。JSON の境界を見直す機会にはなるが、すべての import を一度に置き換える理由にはならない。ここではレビュー計画を提案する。Go の移行やベンチマークは実施していない。

## 二つの判断を分ける

[リリースノート](https://go.dev/doc/go1.27#encodingjsonv2)によれば、既存の `encoding/json` API は引き続きサポートされ、新しい実装でも動作を維持する。ただしエラーの文面は変わる可能性がある。ツールチェーンの更新と v2 の意味論の採用には、それぞれ別の証拠が必要になる。

まず各境界で実際に使うツールチェーン、import、オプションを記録する。import を変更する前に既存の契約テストを実行する。エラー全文を比較するテストは、その文面が公開された契約なのか、偶然の実装詳細なのかを判断したい。ビルドを通すためだけにアサーションを削除せず、要求が動作にあるなら、その動作を確認する形に置き換える。

## 入力の受理と出力を別々に試す

[v2 のリファレンス](https://pkg.go.dev/encoding/json/v2)は、既定で重複したオブジェクト名と不正な UTF-8 を拒否すると説明している。以前受け入れていたデータを再確認する価値がある。同じシリアライザーによる往復が成功しても、別の生成側から届く入力の境界テストにはならない。

通常のリクエスト、重複名、不正な文字列、大文字小文字の異なるフィールド名、そして欠落、null、空のコレクション値を含む小さな合成データ集を用意する。各ケースの受理結果とデコード後の意味を記録し、出力 JSON は実際の利用側の期待と別に照合する。個人情報、認証情報、本番環境からコピーしたデータをフィクスチャに含めない。

## 例外をレビュー可能にする

互換性の要件を説明できる担当者と、一つの境界から移行する。旧動作を維持するオプションを使うなら、影響する生成側、必要な理由、削除条件を記録する。どの契約が旧動作に依存しているのかを隠す全体設定は避けたい。

性能評価は別に行う。バージョン、入力の形、オプションを固定してから、重要なワークロードを測定する。互換性テストの合格は高速化も普遍的な安全性も証明しない。有用なレビューには、明確な受理マトリクス、利用側の確認、ロールバックの判断が残る。import パスの変更だけで終わらせない。
