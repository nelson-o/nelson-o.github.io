[2026 年 9 月 9 日公開の React 19.3](https://react.dev/blog/2026/09/09/react-19-3)では、Fragment refs が安定版になった。ラッパーとなる DOM 要素を増やさず、命令的な操作を行える。本稿は 11 月 12 日時点での既存機能の評価であり、新リリースの速報でも、実施済みの移行報告でもない。

ref を置くためだけに追加したラッパーなら、削除の候補になる。一方、レイアウトや意味のある構造を担うラッパーには別の判断が必要だ。消せる要素の数ではなく、その要素の仕事からレビューを始めたい。

## 操作の窓口とコンテナーを分けて考える

見出しと複数のコントロールを返す結果コンポーネントを考える。親は結果へフォーカスを移したいが、子要素は外側のレイアウトへ直接参加させたい。このような場面では Fragment ref を評価する価値がある。

変更前に、既存コンテナーの CSS セレクター、位置指定の前提、イベントハンドラー、アクセシブルな名前、テストのロケーターを洗い出す。なくせる責任と、実際の要素が必要な責任を分ける。命令的な操作の窓口だけでは、見出し、名前付き領域、フォームのグループを代替できない。

意図した意味を担うマークアップは残す。問題がコンポーネント API の使いにくさだけなら、限定した操作を公開する方法と、呼び出し側に広いグループへのアクセスを渡す方法を比較する。ラッパーの削減が、責任範囲の暗黙の拡大にならないようにしたい。

ref には `<>` ではなく明示的な `<Fragment ref={...}>` 構文が必要で、得られるハンドルは `HTMLElement` ではなく `FragmentInstance` になる。[API リファレンス](https://react.dev/reference/react/Fragment)を参照したい。

## フォーカス先はプロダクトの判断にする

[Fragment のリファレンス](https://react.dev/reference/react/Fragment)では、`focus()` は入れ子の子要素を深さ優先で探し、最初のフォーカス可能なノードへ移動する。一方、イベントリスナーとオブザーバーの対象は第 1 階層の DOM 子要素だ。

結果コンポーネントで「結果にフォーカスする」とは何か。主要操作なのか、失敗時の再試行ボタンなのか、読み込み後に使えるコントロールなのか。グループへの汎用操作が役立つのは、関連するすべての状態で意図した対象になる場合だ。

二つのコントロールを持つテストを計画し、その前に新しいコントロールを挿入する。先頭の無効化、空の結果、条件付きのエラー操作でも試す。ユーザー操作の後にどの要素がフォーカスされたか記録する。通常の Tab 移動も確認したい。命令的な移動の成功だけでは、残りのキーボード経路が適切とは言えない。

子の順番にかかわらず特定の操作へ移す必要があるなら、コンポーネントの契約に対象を明示する。偶然のソース順を、後の貢献者が知らない制約にしない。

## イベントと監視は別々に確認する

「グループへの ref」を「普通のコンテナー要素一つ」と読み替えない。イベント連携では、ハンドラーの target に関する前提、伝播の利用方法、登録と解除を担当する層を記録する。古いラッパー上のリスナーを置き換える前に、選んだ API がその期待を満たすか確認する。

オブザーバー連携では、領域全体の結果が一つ必要なのか、各要素の観測が必要なのかを決める。観測をコンテンツの読み込みや可視状態の更新へどう結び付けるか書き出す。集約規則は設計で決めるべきであり、小さなデモでたまたまコールバックが一度だけ発生したことから推定しない。

マウント、子の追加と削除、グループのアンマウントをテストする。繰り返しも含め、重複登録や古い監視が見つかるようにする。これらは提案する確認項目であり、本稿で実施した Fragment-ref 実験の結果ではない。

## 複数の証拠で同じ変更を確認する

| 関心事 | 提案する変更前後の証拠 |
| --- | --- |
| レイアウト | 同じ外側の grid または flex、狭い画面、長い内容 |
| 意味 | 意図した見出し、名前、グループが維持されること |
| フォーカス | 読み込み、エラー、空の結果、並べ替え時の指定対象 |
| イベントと監視 | 反復変更でのコールバック、集約、解除が意図どおりであること |

スクリーンショットは、ラッパー削除によるレイアウトの変化を示せる。キーボード操作の記録は、フォーカス先を示せる。どちらも他方の結果を証明しない。最終 DOM と関連するアクセシビリティ情報も確認し、失敗をレビューから隠さない。

採用判断には正確な React と連携側のバージョンを記録し、小さく戻せる手段を残す。本稿では依存関係の更新、ベンチマーク、アクセシビリティ監査を実施していない。目指すのは必要なマークアップを保った明確な契約であり、コンテナーを一律に Fragment へ置き換えることではない。
