公開されている Agent Skill の情報源を見ると、かつてはプロンプトやレビューの習慣、チームの記憶に留まっていた指示が、再利用できる形にパッケージ化されつつある。注目すべき変化はモデルそのものではなく、その周辺にある。エンジニアリングプロセスの一部が、検査可能な成果物になりつつあるのだ。

**Agent Skill** とは、`SKILL.md` ファイルを中心に、必要に応じてスクリプト、参考資料、アセットを含むディレクトリである。メタデータによって、いつ読み込むべきかをエージェントに伝えられる。完全な指示と補助リソースは、必要になったときにだけ読み込まれる。

この段階的な構造は [Agent Skills 仕様](https://agentskills.io/specification) で定義され、[Anthropic](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)、[OpenAI](https://learn.chatgpt.com/docs/build-skills)、[GitHub](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/add-skills) も、それぞれのエージェント環境向けに文書化している。

私は Skill が開発の一つのレイヤーになりつつあると考えている。汎用エージェントと、リポジトリで実際に行う作業の間に置かれる、保存されたエンジニアリング手順である。ただし、「最も人気のある Skill」のランキングを作れば、公開カタログからは得られない根拠があるかのように見えてしまう。

より擁護しやすい指標は反復性である。この限定的なサンプルでは、調査したパッケージがワークフローのゲートを繰り返し明示していた。

私はこれを、開発者がエージェントの自由をどこで制約したいのかを示す手がかりと捉えている。独立した収束の証明ではない。

## この調査をどのように構成したか

調査期間は 2026 年 4 月 27 日から 7 月 27 日までとし、根拠は 7 月 28 日に取得した。サンプルには、ファーストパーティまたはリポジトリ所有者による文書 12 件と、直接確認した Skill ファイル 5 件が含まれる。

カタログは、リポジトリまたはソースファイルへの参照がある場合に限って数えた。

次の 4 つのシグナルは、利用状況の測定値ではなく代理指標として扱った。

- **可視性：** パッケージが、所有者またはメンテナーによる公開情報源に掲載されている。
- **メンテナンス：** 日付が確定した変更不能なリリースまたはコミットが、調査期間内に存在する。
- **反復性：** 指示が、繰り返し使われる手順、ゲート、チェックを明文化している。
- **再利用性：** 情報源が、再利用可能なパッケージまたは配布経路を文書化している。

これらのシグナルから分かるのは、あるワークフローパターンが可視化され、再利用向けにパッケージ化されていることまでである。インストール数、実際の利用、効果は分からない。

Star 数、レジストリの件数、マーケットプレイスでの掲載位置、二次的なディレクトリは、採用状況の根拠として使わなかった。

さらに 2 つの制約が重要である。調査した 5 つの候補のうち 4 つは [Superpowers repository](https://github.com/obra/superpowers) のものであり、このサンプルは一つの一貫した方法論を深く捉える一方、競合するプロセスパックの把握には弱い。

ソースファイルは締切後に取得した、変更可能なブランチ上の表示だった。したがって、どの候補についても調査期間内のメンテナンスは**確認できなかった**。

リポジトリの [release notes](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md) は締切後の調査には利用したが、調査期間内のメンテナンスを示す根拠にはしていない。

表中の可視性、反復性、再利用性は、人気度の定性的な代理指標である。どの行も採用状況を測定してはいない。

## Domain Skill の並行した台頭

Process Skill は、作業を**どのように**進めるかを制約する。Domain Skill は、エージェントが**どこを**調べ、どの専門知識を信頼してよいかを制約する。

[Anthropic の公開 Skill リポジトリ](https://github.com/anthropics/skills) には、技術、文書、エンタープライズ向けのパッケージが含まれている。

OpenAI の [`openai-docs`](https://github.com/openai/skills/blob/main/skills/.curated/openai-docs/SKILL.md) Skill は、より対象が狭い。OpenAI と Codex に関する質問では、一般的な Web 上の記憶ではなく、公式ドキュメントと専用のドキュメントツールへエージェントを誘導する。

これは Domain Package というパターンを裏づける情報源ベースの根拠であり、市場全体での台頭を証明するものではない。

私は、この 2 つのカテゴリーは相互補完的だと考えている。Debugging Skill は調査方法を統制し、Framework や Vendor の Skill は調査中に使う事実を統制する。

Domain Package は本質的に移植性も低い。その価値が、指定された情報源やツールへアクセスできるかどうかに左右されるためである。

## 詳細な確認で見方がどう変わったか

5 つの候補 Skill を、架空の開発タスクで実行することはしなかった。そのうち 4 つは、ファイルの書き込み、コマンドの実行、コミット、別のエージェントへの作業引き継ぎをエージェントに指示しうる。

Domain Skill は、リモートのドキュメントを取得したり、ローカル環境のセットアップを提案したりできる。

決定論的な Runner がないまま結果をシミュレーションすれば、実態以上に実証的に見えてしまう。ここでの所見はファイル確認だけに基づき、実作業での性能結果でもベンチマークスコアでもない。

それでも、ファイルを読むことで、有用な単位に対する見方は変わった。[`brainstorming`](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md) は創造性を促すプロンプトではない。質問、代替案、承認、設計文書、レビューを明文化している。

[`test-driven-development`](https://github.com/obra/superpowers/blob/main/skills/test-driven-development/SKILL.md) は、「テストを先に書く」を、失敗するテストより前に本番コードを書くことの禁止へ変える。[`systematic-debugging`](https://github.com/obra/superpowers/blob/main/skills/systematic-debugging/SKILL.md) は、順序立てた因果関係の調査を守る。

[`verification-before-completion`](https://github.com/obra/superpowers/blob/main/skills/verification-before-completion/SKILL.md) は、完了の主張を最新の出力に結びつけるという、狭い役割を担うため、比較的コンパクトである。

[`openai-docs`](https://github.com/openai/skills/blob/main/skills/.curated/openai-docs/SKILL.md) は、一つの領域における情報源への誘導と、範囲を限定した不確実性に、かなり多くの指示を割いている。

5 つすべてに共通して、Skill 自体が自律的な専門知識を提供するわけではない。制約するのは意思決定の局面である。実装前に定義し、修正前に失敗を観察し、パッチを当てる前に原因を説明し、主張する前に検証する。

Domain Skill が制約する意思決定は、回答前に権威ある情報源を確認することである。

コンテキストのコストも重要である。[仕様](https://agentskills.io/specification) が推奨するように、Progressive Disclosure はメタデータを軽量に保ち、起動されるまで本文全体や参考資料の読み込みを遅らせる。

狭いトリガーと分割された参考資料は、単なるドキュメント整理ではなく運用上の設計判断だと私は推測している。この調査では特定モデルの Token 数を測定していないため、この推測を数値的な主張にはしない。

## 人気度が実際に示すこと

この調査で限定的に定義した人気度の範囲では、繰り返し現れる Skill は、再利用可能なプロセスインフラのように見える。

チームが重視する質問、ゲート、チェックを、長い System Prompt やシニアエンジニアの記憶に残すのではなく、検査可能でバージョン管理可能にする。

複数クライアントにまたがる文書は示唆的である。[OpenAI は ChatGPT デスクトップ、Codex CLI、IDE 拡張機能にまたがる Skill を文書化している](https://learn.chatgpt.com/docs/build-skills)。

[GitHub は Copilot の Cloud Agent、Code Review、CLI、App、VS Code Agent Mode にまたがって Skill を文書化している](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/add-skills)。[Superpowers は複数ホスト向けのインストール方法を公開している](https://github.com/obra/superpowers)。

私は、ワークフローパッケージがクライアントの境界を越えつつあると推測する。挙動が同一であることや、普遍的なインストール先があることまでは推測しない。

最も強く共有されている設計上の選択は、壊れやすい局面で自由を制約することである。

ゲートとゲートの間では、エージェントは生成能力を保つ。しかし、曖昧さ、確証バイアス、早すぎる完了が最も危険になる場面では、Skill が責任ある次の行動の範囲を狭める。

手順を実行可能にすることにはコストがある。Skill はスクリプトを含み、ツールを直接呼び出し、限られたコンテキストを消費し、リポジトリの指示と重複する場合がある。GitHub のドキュメントは、使用前に同梱内容を確認するよう明示的に推奨している。

私は Skill をサプライチェーンへの入力として扱う。内容を検査し、トリガーと権限を理解し、再現性が重要なら既知の Revision に固定する。

## 最初に導入する構成

既存のエンジニアリングチームに Skill を導入するなら、カタログ全体をコピーするのではなく、次の 5 つの能力から始める。

1. **要件の明確化：** 実装前に前提、代替案、スコープ、承認を明らかにする。
2. **計画とコンテキスト：** 承認済みの設計を小さなステップに分け、リポジトリの知識は関連するときだけ読み込む。
3. **テスト駆動実装：** テスト可能な作業で挙動を変える修正を行う前に、観測可能な失敗を必須にする。
4. **体系的デバッグ：** 再現し、根拠を集め、一つの仮説を立て、パッチを当てる前に原因を検証する。
5. **検証とレビュー：** 完了を示す最新の根拠を集め、レビューを独立した明示的な境界にする。

この構成なら、すべてのタスクにすべてのゲートが必要だと装うことなく、ワークフローを網羅できる。各 Skill をプレビューし、そのスクリプトとツールへの指示を確認し、ソースの Revision を固定したうえで、一度に一つの能力を導入する。

次に、代表的な依頼でトリガーをテストする。読み込むべき場合、何もしないべき場合、リポジトリのルールに従うべき場合を確かめる。

重複も取り除く。リポジトリの指示、ホストポリシー、Skill が同じゲートをそれぞれ異なる形で定義していれば、指示を増やすほど挙動の予測可能性が下がりうる。

一貫性を保てる最小の情報源が、最も検査しやすく、保守しやすい。

## Skill が残す問い

問うべきなのは、カタログの最上位にある Skill ではない。エンジニアリングプロセスのどの部分を明示的で再利用可能、かつ検査可能にする価値があるのか。そして、どの部分は判断に依存し、目に見える形で人間の手に残すべきなのかである。
