[2026年6月23日のVite 8.1発表](https://vite.dev/blog/announcing-vite8-1)では、実験的なchunk import mapが紹介された。本稿は11月10日に確認した公式ドキュメントを基に、既存機能の採用判断を考えるものだ。新リリースの速報でも、実測した性能改善の報告でもない。

問うべきなのは、不要なチャンク変更を減らす効果が、追加のリリース検証に見合うかどうかだ。更新量が小さくても、デプロイ前後や切り替え中に、利用者が整合したアプリケーションを読み込めなければ十分ではない。

## チャンクの識別子と現在のURLを分ける

[Rolldownのドキュメント](https://rolldown.rs/reference/InputOptions.experimental#chunkimportmap)は、内容のハッシュに依存しないチャンクキーを説明している。Import mapがキーを生成ファイルに対応づけ、依存先のファイル名変更だけで生じる連鎖的な変更を減らす。

この仕組みは、具体的な実験で評価できる。小さな末端モジュールだけを変更し、前後のビルドを比較する。どのファイルが変わり、圧縮後の変更バイト数はいくつで、代表的なルートがそのうち何を取得するのか。改名されたファイル数だけでは、小さなファイルやそのルートで使われないファイルの効果を大きく見積もりかねない。

意図的な変更以外は、ソースの版、ロックファイル、ビルド設定、圧縮条件を固定する。オプション無効時と有効時をそれぞれ比較する。これは測定の提案であり、本稿のためにViteのビルド実験を実行したわけではない。

## 実験的な機能という境界を残す

現在の[Vite設定リファレンス](https://vite.dev/config/build-options#build-chunkimportmap)では、`build.chunkImportMap`は実験的で、既定では無効、`import.meta.resolve`の対応が必要とされる。したがって、リリースレビューでは対象ブラウザーを明記すべきだ。ビルド成功とブラウザー互換性は同じ証拠ではない。

[機能ガイド](https://vite.dev/guide/features#chunk-import-map-optimization)によれば、CSSとアセットにはこの最適化が完全には適用されない。アセットを変更すると参照元のチャンクは変わり得るが、その無効化がさらに上の参照元へ連鎖するとは限らない。

こうした制約は、全アプリケーションへの一括適用よりも、小さな試行に向いている。比較にはJavaScriptだけの変更と、アセットまたはスタイルの変更を含める。日常のリリースで画像やスタイルの変更が多いなら、JavaScriptの結果だけでは通常の更新コストを説明できない。

8.1の発表では、当時`experimental.renderBuiltUrl`とこのオプションを併用できないとも記されていた。配信が独自のURL書き換えに依存するなら、採用を計画する前に、対象の正確な版でその組み合わせを確認する。

## 文書と参照ファイルを一つのリリースとして扱う

対応表があっても、古い文書が自動で新しいリリースになるわけではない。開いたままのタブは、読み込んだ版のファイルを後から必要とすることがある。同じ公開URLでも、新しいタブと古いタブは別のテストケースになる。

Viteの[本番ビルドガイド](https://vite.dev/guide/build#load-error-handling)は、以前のデプロイのアセットが削除された後の動的インポート失敗を扱い、HTMLを`Cache-Control: no-cache`で再検証するよう勧めている。これはレビューの背景であり、一つのキャッシュヘッダーが古いタブの問題をすべて解決する証明ではない。

採用を検討するときは、ホストが新しいファイルを用意し、入口の文書を切り替え、旧ファイルを保持し、前の版へ戻す方法を記録する。実際の応答ヘッダーとアセットの挙動を確認し、アプリケーション設定がCDNを制御できると決めつけない。これは運用レビューの提案であり、このサイトのホスティングやセキュリティ設定を変更するものではない。

次の小さな受け入れ表で違いを明確にできる。

| 状況 | 残すことを提案する証拠 |
| --- | --- |
| 更新後の新しいブラウザー | 入口文書、要求されたチャンクURL、正常なルート表示 |
| 更新前から開いたタブで遅延ルートへ移動 | 古い参照が解決するか、意図した復旧経路が用意されている |
| 切り替え中のキャッシュ済み文書 | 明示した保持期間中に参照ファイルを取得できる |
| ロールバック | 復元した文書と必要なファイルで前の版が動作する |

古いタブのテストには、現実的な未完了操作を含める。強制再読み込みで画面が正常になっても、フォーム入力を失うなら安全な復旧とは異なる。再読み込みなら何でも成功とせず、望む動作を明確に決めるべきだ。

## PRには二種類の証拠を求める

最適化のレビューには、キャッシュの比較とリリース整合性の確認を両方含める。正確なViteの版と設定値、制御したソース変更、圧縮後の変更バイト数、対象ブラウザー、ファイル保持とロールバックの前提を記録する。良い結果とともに、失敗や未検証の組み合わせも示す。

エージェントは証拠収集を手伝える。しかし、bundleが小さいという説明だけでは、古いセッションがデプロイをまたいで使えるとは証明できない。採用を元に戻せる形にし、確認した効果が互換性や運用の負担に見合わなければ無効のままにする。不要な転送を減らしながら、リリースの挙動を説明しやすく保つことが目的だ。
