エージェントの時代に問うべき中心は、役に立つコードを書けるかどうかでは、もうない。エージェントは書ける。より難しい問いは、もっともらしい実装を出すことより、その実装をシステムに残すべきかを判断するほうが高くつくとき、私たちがどう働くかだ。

## ボトルネックは移動した

これまでエンジニアリングの多くは、意図を動く変更へ変換することに費やされてきた。エージェントはこのループを圧縮する。リポジトリを調べ、実装の下書きを作り、フィードバックに応じて素早く直せる。変わるのは、単なる入力速度ではなく、変更がチームに届く速度だ。

コードが潤沢になると、複雑性を制御することがエンジニアリングの仕事になる。

希少になるのは判断だ。何を変えるべきか、何を安定させるべきか、そして pull request の新しさが消えた後にシステムが何を所有できるかを決める判断である。

## コードの重要性は変わりつつある

コードは今も人が理解すべき成果物だ。同時に、機械が安全に調べ、変更し、テストし、復旧できる基盤にもなっている。そのため、明確な境界、予測可能な構造、局所的な変更、実行可能なチェック、repository-native なコンテキスト、明瞭な所有権とロールバック経路の価値が上がる。

人間にとっての可読性が不要になるわけではない。それはより広い要件の一部になる。コードベースは人が統治でき、機械が安全に運用できなければならない。エージェントは変更できてもチームが説明できないシステムは、適応的なのではなく、ただ速く動いているだけだ。

## 安いコードは高価な複雑性を生む

エージェントはコードを追加するコストを下げるが、それを長く所有するコストまでは下げない。もっともらしい実装でも、不要な抽象を導入し、既存の概念を重複させ、変更範囲を広げ、将来の保守者やエージェントが再構成すべき意図を隠しうる。

生成コストはゼロに近づく。所有コストはそうではない。

だから生成されたスロップは見た目だけの問題ではない。理由のない層が一つ増えるごとに、学ぶルール、テストする分岐、将来の変更が予想外に失敗する場所が増える。コードが早く現れるほど、どの複雑性を残してよいかを慎重に決める必要がある。

## チェック通過だけでは良い変更にならない

validation と verification は不可欠な証拠を与える。期待する振る舞い、型の一貫性、ビルド互換性、既知の不変条件を示せる。しかし、抽象が正当化されるか、変更が不必要に広いか、コードが意図を最も明快に表しているかまでは決められない。

verification が問うのは変更が動くかどうかであり、review が問うのはその変更を私たちが所有すべきかどうかだ。

機械的なチェックは早く、頻繁に走らせるべきだ。その成功は質的な review を省く許可ではない。自動化を疑うのではなく、自動化が実際に果たせる役割を与え、設計上の判断を見えるままにする。

## 開発者が品質ゲートになる

この変化を「開発者はエージェントのオーケストレーターになる」とだけ言うのは浅い。開発者は意図と制約を定義し、仕事を分解し、エージェントのタスクを境界づけ、実装を review して修正し、guardrail と受け入れ基準を書き、production の結果を所有する。

これは各境界で能動的に働く役割だ。良い prompt は仕事を始められるが、弱い設計を拒むこと、diff を小さくすること、抽象を取り除くこと、リスクに見合う証拠を求めることの代わりにはならない。

## エージェント開発のゲート付きワークフロー

エージェントの速度を有用に保つ workflow には、明確なゲートの連なりが必要だ。

```text
意図
  -> 設計ゲート
  -> 境界づけたエージェントタスク
  -> 小さく review 可能な変更
  -> 人間による review と修正
  -> validation と verification
  -> merge
  -> production フィードバック
```

順序には意味がある。低コストなチェックはループ全体で走らせてよいが、最終的な validation と verification は、意図的な人間の review と修正の後に置く。review のフィードバックは仕事をエージェントへ戻し、production の証拠は次の設計ゲートとタスク境界を強くする。これはウォーターフォールではない。スピードを所有権につなげ続ける、制御されたループである。

## スロップがアーキテクチャになる前に止める

最も有効な guardrail は、生成結果が既定の設計として固まる前に、通常のエンジニアリング規律を適用することだ。大きな生成の前に設計または変更契約を求める。大きすぎる、またはスコープが弱い pull request を拒む。ファイル、dependency、アーキテクチャの境界を定める。一つの包括的な投げ込みより、筋の通った小さな変更を複数選ぶ。

エージェントには review のフィードバックへ応答させ、単に patch を重ねるのでなく出力を簡潔にさせる。説明できない複雑性は要件不達とみなす。merge の前にはリスクに見合う証拠を求める。すべての変更に同じ証明は要らないが、すべての変更には `main` に入れる理由を説明できる責任がある。

## シニア開発者とエンジニアリングリードに起きる変化

シニア開発者は最初の実装を打ち込む時間を減らし、境界を形づくること、抽象を問い直すこと、出力を修正すること、人とエージェントの双方が安全に変更できる面を改善することに多くの時間を使うようになる。仕事はよりアーキテクチャ寄りになるが、実践から離れるわけではない。

エンジニアリングリードは、生成のスループットが review の能力を追い越さないようデリバリーシステムを設計し直す必要がある。測るべきなのは、生成行数、エージェント実行数、pull request 数ではなく、review 済みで verification 済み、かつ保守可能な成果だ。review と修正の容量は、システムの実際の生産能力の一部である。

## エンジニアリングレバレッジの新しい定義

最も強いエージェント時代のエンジニアは、最も多くのコードを出す人ではない。機械の速度を保守可能な変更へ変え、複雑性を見えないまま積み上げない人だ。

エンジニアリングレバレッジとは、生成コードの量ではなく、複雑性を防ぎ、形づくり、安全に所有する能力である。
