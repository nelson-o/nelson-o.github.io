エージェント時代に最初に考えるべきことは、エージェントが役に立つコードを書けるかどうかではない。すでに書ける。難しいのは、もっともらしい実装を出すよりも、それをシステムに残す価値があるかを見極めるほうが高くつくとき、開発の進め方をどう変えるかだ。

## ボトルネックは移動した

これまでエンジニアリングの多くは、意図を動く変更に変えることに費やされてきた。エージェントはこのループを短縮する。リポジトリを調べ、実装のたたき台を作り、フィードバックに応じて素早く直せる。変わるのは単なる入力速度ではなく、変更がチームに届くまでの速さだ。

コードが潤沢になると、複雑性を制御することがエンジニアリングの仕事になる。

希少になるのは判断である。何を変えるべきか、何を安定させるべきか、そして Pull Request の提出から時間がたっても、システムが何を抱え続けられるかを決める判断だ。

## コードの重要性は変わりつつある

コードは今も人が理解すべき成果物だ。同時に、機械が安全に調べ、変更し、テストし、復旧できる土台にもなっている。だからこそ、明確な境界、予測可能な構造、局所的な変更、実行可能なチェック、リポジトリに根差したコンテキスト、明瞭な所有権とロールバック経路の価値が上がる。

人間にとっての可読性が不要になるわけではない。それはより広い要件の一部になる。コードベースは人が統治でき、機械が安全に運用できなければならない。エージェントは変更できてもチームが説明できないシステムは、適応的なのではなく、ただ速く動いているだけだ。

## 安いコードは高価な複雑性を生む

エージェントはコードを追加するコストを下げるが、それを長く保守し続けるコストまでは下げない。もっともらしい実装でも、不要な抽象を増やし、既存の概念を重複させ、変更の影響範囲を広げ、将来の保守者やエージェントが読み解くべき意図を隠しうる。

生成コストはゼロに近づく。所有コストはそうではない。

だから生成されたスロップは見た目だけの問題ではない。理由のない層が一つ増えるごとに、学ぶルール、テストする分岐、将来の変更が予想外に失敗する場所が増える。コードが早く現れるほど、どの複雑性を残してよいかを慎重に決める必要がある。

## チェック通過だけでは良い変更にならない

バリデーションと検証は不可欠な証拠を与える。期待する振る舞い、型の一貫性、ビルドの互換性、既知の不変条件を示せる。しかし、抽象が正当化されるか、変更が不必要に広いか、コードが意図を最も明快に表しているかまでは決められない。

検証が問うのは、変更が動くかどうかだ。レビューが問うのは、その変更を私たちが引き受けるべきかどうかである。

機械的なチェックは早く、頻繁に走らせるべきだ。その成功は、質的なレビューを省く理由にはならない。自動化を疑うのではなく、自動化に果たせる役割を任せ、設計上の判断を見えるままにする。

## 開発者が品質ゲートになる

この変化を「開発者はエージェントのオーケストレーターになる」とだけ言うのは浅い。開発者は意図と制約を定義し、仕事を分解し、エージェントのタスクに境界を設け、実装をレビューして修正し、ガードレールと受け入れ基準を定め、本番環境で起きる結果を引き受ける。

これは各段階で能動的に働く役割だ。良いプロンプトは仕事を始める助けにはなるが、弱い設計を拒むこと、差分を小さくすること、抽象を取り除くこと、リスクに見合う証拠を求めることの代わりにはならない。

## エージェント開発のゲート付きワークフロー

エージェントの速さを活かすには、明確なゲートを備えたワークフローが必要だ。

```text
意図
  -> 設計ゲート
  -> 範囲を限定したエージェントタスク
  -> 小さくレビュー可能な変更
  -> 人によるレビューと修正
  -> バリデーションと検証
  -> マージ
  -> 本番環境からのフィードバック
```

順序には意味がある。低コストなチェックはループ全体で走らせてよいが、最後のバリデーションと検証は、人が丁寧にレビューし修正した後に置く。レビューのフィードバックは仕事をエージェントへ戻し、本番環境から得る証拠は次の設計ゲートとタスクの境界を強くする。これはウォーターフォールではない。速さを、引き受ける責任と結び続ける制御されたループである。

## スロップがアーキテクチャになる前に止める

最も有効なガードレールは、生成結果が既定の設計として固まる前に、日頃のエンジニアリング規律を適用することだ。大きく生成する前に設計または変更の契約を求める。大きすぎる、またはスコープが曖昧な Pull Request は拒む。ファイル、依存関係、アーキテクチャの境界を定める。一度にまとめて投げ込むより、筋の通った小さな変更を複数選ぶ。

エージェントにはレビューのフィードバックへ応答させ、単にパッチを重ねるのでなく出力を簡潔にさせる。説明できない複雑性は要件を満たしていないものとみなす。マージの前にはリスクに見合う証拠を求める。すべての変更に同じ証明は要らないが、各変更のオーナーは、なぜ `main` に入れるのかをチームに説明できなければならない。

## シニア開発者とエンジニアリングリードに起きる変化

シニア開発者は最初の実装を打ち込む時間を減らし、境界を形づくること、抽象を問い直すこと、出力を修正すること、人とエージェントの双方が安全に手を入れられる仕組みを改善することに、より多くの時間を使うようになる。仕事はよりアーキテクチャ寄りになるが、実践から離れるわけではない。

エンジニアリングリードは、生成のスループットがレビューの能力を追い越さないよう、デリバリーの仕組みを設計し直す必要がある。測るべきなのは、生成行数、エージェントの実行数、Pull Request 数ではなく、レビュー済みで検証済み、かつ保守可能な成果だ。レビューと修正の余力は、システムの実際の生産能力の一部である。

## エンジニアリングレバレッジの新しい定義

最も強いエージェント時代のエンジニアは、最も多くのコードを出す人ではない。機械の速度を保守可能な変更へ変え、複雑性を見えないまま積み上げない人だ。

エンジニアリングレバレッジとは、生成コードの量ではなく、複雑性を防ぎ、形づくり、安全に所有する能力である。
