## フィルターを一つ追加する

「フィルターを一つ追加する」は、今も小さなフロントエンドの依頼に見える。チケットのタイトルに収まり、画面上ではツールバーに20ピクセルほどの部品が増えるだけかもしれない。

しかし、依頼はプロダクト上の問いから始まる。誰が必要としているのか。どのデータを含めるのか。初期値は何か。検索条件と併用するのか。役に立ったと何で判断するのか。

プロダクトマネージャーは、問いをユーザーの目標、受け入れ条件、計測指標、ロールアウト計画に落とし込む。デザインも正常系だけでなく、空、読み込み中、エラー、狭い画面での状態まで定義する。

エンジニアリング側は、条件を URL、ローカル状態、共有ストアのどこに置くかを決める。API にはクエリパラメータ、schema、ページング規則、該当データがない場合の応答が必要になるかもしれない。

コンポーネントは変更の一部にすぎない。テスト、テレメトリ、フィーチャーフラグ、リリースノート、ロールバックの手段も同じくらい重要になり得る。

これは、未来から変化を振り返る話ではない。エージェント型エンジニアリング（agentic engineering）が立ち上がり始め、チームが進め方を組み立てている現在の話だ。

## エージェントがすでに変えたこと

エージェントはリポジトリを検索し、似たフィルターを見つけ、コンポーネントと API クライアントを追い、複数ファイルを変更し、テストの下書きまで作れる。

以前なら開発者がコンテキストを集めている間に、最初の差分ができる。この速さは、すでに日々の仕事を変えている。

開発者は初版を依頼し、差分を読み、抜けた状態を指摘し、変更範囲を小さくするよう頼める。すべての行を自分で入力する必要はない。

プロダクトとデザインも、早い段階で案を確かめられる。操作できるプレビューがあれば、不明確な初期値、欠けた権限ルール、使いにくいモバイル操作を本開発の前に見つけられる。

ただし、出力が速くても依頼が解決したとは限らない。既存の不具合をまねたり、不要な抽象化を選んだり、自分の仮定に合わせてテストを書いたりすることもある。

変更した箇所だけを見れば正しくても、隣のワークフローを壊すこともある。

新しい能力はすでにある。それを使う仕事の型は、まだ成熟していない。

## 日々の進め方を組み直す

実用的なエージェント型ワークフローは、プロンプトの前から始まる。まず、ユーザーの目標、対象画面、期待する状態、API の挙動、対象外、リリースに必要な証拠を書き出す。

エージェントには、範囲を限定したタスクとリポジトリの指示を渡す。求めるのはレビューできる差分であり、同じ PR でコンポーネント基盤、依存関係、無関係なテストまで作り直すことではない。

開発者は設計と実装の両方を見る。URL は共有できるか。サーバー側ページングは保たれているか。既存のデザインシステムを使っているか。権限は UI で隠すだけでなく、バックエンドで検証されるか。

自動チェックは目的別の証拠を出す。契約テストはリクエストとレスポンスの前提を、コンポーネントテストとアクセシビリティテストは各状態とキーボード操作を検証する。

End-to-end テストはユーザーから見える一連の操作を確かめる。プレビューではプロダクト、デザイン、エンジニアリングが同じビルドを確認できる。

フィーチャーフラグは公開範囲を制限する。テレメトリは利用状況とエラーを示す。ロールバックの手段は、本番環境がテスト環境と違う動きをしたときにリリースを守る。

本番で得た情報は次の変更に戻す。見逃したエッジケースは、受け入れ条件、テストデータ、コンポーネント API、リポジトリのガイドを改善する材料になる。

## 分担は変わるが、責任は残る

エージェント型開発は専門家の責任をなくさない。各分野がどこに注意を使い、その判断をどう実装へ届けるかを変える。

| 役割 | 新しいワークフローで担う具体的な責任 |
| --- | --- |
| プロダクトマネージャー | ユーザーの目標、優先順位、受け入れ条件、成功指標、ロールアウト、その後の判断を定義する |
| デザイナー | 操作状態、アクセシビリティ、レスポンシブ規則、プロダクトの言葉を定義する |
| フロントエンドエンジニア | ブラウザの挙動、状態、レンダリング、性能、デザインシステムの利用、UI 検証を担う |
| バックエンドエンジニア | ドメインルール、認可、データ整合性、API 契約、運用上の制限を担う |
| フルスタックエンジニア | UI、サービス、データ、テスト、リリースをまたいで依頼を追う |
| プラットフォームエンジニア | コンポーネント API、型付きクライアント、リポジトリのガイド、CI、プレビュー、可観測性を整備する |

これらの責任は開発中に重なる。プロダクト判断は API の形式に影響し、バックエンドの制限は操作設計に影響する。

UI のエラー状態から、サービス契約が「該当なし」と「リクエスト失敗」を区別できないと分かることもある。

エージェントはファイルをまたいで情報を運べる。しかし、どのトレードオフをチームが引き受けるかを黙って決めることはできない。その判断には担当者と追跡できる記録が要る。

## ガードレールも機能開発の一部

プラットフォーム整備と機能開発は別の仕事として扱われがちだ。エージェントが開発に入ると、両者のつながりは無視しにくくなる。

明確なコンポーネント API は、よく似たフィルターがまた増えるのを防ぐ。自動生成クライアントは UI コードをサービスの schema に合わせる。テストデータは権限切れや、ページング後の空ページを再現する。

リポジトリの指示は守るべきパターンを示す。CI は型エラー、契約のずれ、アクセシビリティの回帰、静的エクスポートの失敗を止める。プレビュー環境は変更そのものをレビュー可能にする。

可観測性はマージ前のテストで見えない部分を補う。実データでのレイテンシ、特定ブラウザの不具合、想定外の空結果、ユーザーが実際にフィルターを使ったかどうかを確認できる。

ガードレールはリスクに比例させる。軽微な文言変更に、新しいクエリ経路と同じ証拠は要らない。ノイズの多いテストや曖昧な指示は人とエージェントの両方を遅くするため、継続的な手入れが必要だ。

目標は明快だ。期待する実装を見つけやすくし、危険な実装を検出しやすくし、リリースを戻しやすくする。

## 新しい進め方に片足を踏み入れた

多くのチームは、完全な手作業から成熟した新方式へ一気に移るわけではない。同じスプリントの中で、新旧の進め方を混ぜている。

あるチケットは手で実装し、次はエージェントが作った差分から始める。別のチケットでは、未知のデータフローを追う、または不具合を再現するためだけにエージェントを使う。

範囲はまだ動いている。タスクにどれだけコンテキストを含めるか、生成する変更をどこまで小さくするか、人がいつ介入するか、どのチェックが儀式ではなく証拠になるかを学んでいる。

日々の習慣も変わる。計画には機械向けの指示が入り、レビューでは生成された抽象化を問い直す。振り返りでは本番へ漏れた不具合をテストデータ、契約、リポジトリ規則の改善につなげられる。

フロントエンド開発は今も、ブラウザ、API、状態、テスト、リリースを扱う具体的な仕事だ。プロダクト管理も、目標、優先順位、受け入れ条件、学習を扱う具体的な仕事である。

エージェント型開発は、それらの判断をより速い実装につなぐ。私たちはすでに一歩踏み込んでいるが、足元の道は今も作っている途中だ。
