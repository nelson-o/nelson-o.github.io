## フィルターを一つ追加する

「フィルターを一つ追加する」は、かつてよくあるフロントエンドの依頼だった。文章はチケットのタイトルに収まるほど短く、目に見える結果もツールバーの20ピクセルほどを占めるだけかもしれない。

これは一つの実在プロジェクトの話ではない。コーディング Agent が日常のワークフローに入る前、多くのフロントエンドコードベースで繰り返された変更を組み合わせたものだ。

最初の問いは、たいていコントロールをどう描画するかではなく、そのフィルターが何を意味するかだった。どのレコードを含めるのか。既存の検索と組み合わせるのか。再読み込み後も残るのか。状態は URL に保存するのか。デフォルトは誰が決めるのか。API が遅いとき、結果が空のとき、古いブラウザで入力の挙動が異なるときはどうするのか。

一つのコントロールが、プロダクトの曖昧さ、データの意味、インタラクション設計、状態の所有権、リリースリスクを露出させることがある。コードは作業の中で目に見える中間部分にすぎなかった。

## ハンドオフの連鎖

エージェント以前のワークフローでは、役割の境界は実装作業が積み上がる場所に沿っていることが多かった。

デザイナーが意図するインタラクションを記述し、フロントエンド開発者がブラウザの挙動に翻訳する。バックエンド開発者がクエリ契約を公開または変更し、両側が噛み合わなければ full-stack 開発者が間をつなぐ。QA、レビュアー、リリース担当者が、部品が全体として成立しているかを確認する。

この境界は有用だったが、同時にハンドオフの連鎖でもあった。それぞれが同じ問題の別の部分についてコンテキストを再構築した。loading state が欠けていればデザインへ戻り、表現できないクエリはバックエンドへ戻る。テストで見つかった不整合は、スクリーンショット、payload、再現手順とともに連鎖を逆方向へ進んだ。

役割名は専門性だけを表していたのではない。高コストな人間の作業がどこで待ち行列になるかも表していた。

## 目に見えない作業

コンポーネントを変更する前に、フロントエンド開発者はメンタルモデルを組み立てる必要があった。

route を見つけ、component tree を追い、state store を特定し、API client を読み、似たフィルターが別の場所でどう動くかを確認し、ドキュメントに残らなかった判断を古い pull request から探す。デザインファイルと現在のプロダクトを比較し、どちらが現実を表しているのかを決めることも含まれた。

ブラウザのタブは作業記憶になった。framework documentation、issue tracker、compatibility table、network trace、部分的にしか関係しない例が並んだ。その隙間を会話で埋めた。実装が始まるころには難しい作業の多くがすでに終わっていたが、その大半は diff に現れなかった。

コンポーネントが表示された後もループは続いた。フィルターの組み合わせを試し、ページを再読み込みし、viewport size を変え、request を調べ、test を修復し、CI を待ち、review に応答し、deploy 後の結果を確認した。「完了」はコードが存在した時点ではない。変更を信頼できるほど不確実性が取り除かれた時点だった。

## プラットフォーム作業はすでに必須だった

チームは個人のスキルだけでこの作業をスケールできなかった。フロントエンドプラットフォームへの投資は、エージェント以前の時代からすでに必要だった。

デザインシステムは繰り返される判断を減らした。コンポーネントライブラリはアクセシビリティとインタラクションの挙動を保持した。型付き API client は契約のずれを可視化した。local tooling はフィードバックループを短縮し、preview environment は branch の再現に依存しない review を可能にした。CI、browser test、visual regression、observability は期待を反復可能な check に変えた。

これらは feature delivery に対して二次的なものと見なされることもあったが、feature delivery を持続可能にしたのはこの仕組みだった。舗装された道があれば、開発者は依頼のたびに button、form、loading state、build configuration、test setup を作り直さずに済んだ。

プラットフォームは主に人間の実装能力を増幅した。コンテキストを集め、経路を選び、変更を書き、check を解釈するのは依然として人だった。プラットフォームはその手動ループを速く、一貫したものにした。

## UI 構築の希少性がなくなる

Agent と UI builder は、このループの経済性を変える。

Agent は repository を検索し、関連するフィルターを見つけ、component を追加し、state を更新し、query parameter を接続し、test の下書きまで一度に作れる。以前なら最初の実装を終える前に、複数の variant を生成できる。長時間の機械的な集中を必要とした複数ファイルの編集が安価になる。

だからといって、作業が自動的に正しくなるわけではない。なくなるのは実装の希少性だ。もっともらしいインターフェースを作ることは、以前のような制約ではなくなる。

この区別が重要なのは、エンジニアリングの役割が、誰がどの成果物を作れるかによって部分的に構成されていたからだ。生成が安価になると、frontend、backend、full-stack という古い境界の説明力は下がる。より難しい境界は、誰が制約を定義し、結果をどう検証するかへ移る。

## 役割の境界が移る

専門性は消えないが、その重心は移動する。

| 役割 | エージェント以前の中心 | エージェント時代の圧力 |
| --- | --- | --- |
| デザイナー | インターフェースの意図を作り、実装へ渡す | state、constraint、token、品質基準を生成システムが理解できる形にする |
| フロントエンド開発者 | ブラウザ向けの挙動を実装する | UI architecture、platform rule、インターフェース固有の検証を形づくる |
| バックエンド開発者 | service と data contract を実装する | 生成された client が容易に破れない domain invariant、運用制限、契約をコード化する |
| Full-stack 開発者 | 両側を実装して境界を越える | 境界をまたぐ変更をオーケストレーションし、統合された挙動が依頼を解決するか検証する |
| プラットフォーム開発者 | 人間の開発者を加速する | 大量に生成される変更を制約し、導き、観測し、検証する |

hierarchy、interaction、accessibility、product language を決めるとき、デザイナーの専門性は変わらず重要だ。フロントエンドの専門家は browser、rendering、performance、interactive state の failure mode を理解している。バックエンドの専門家は domain behavior、security、data integrity、運用上の結果を所有する。full-stack engineer は、片側だけからは見えない integration gap を見つける。

変わるのは、その専門性を表現するために各役割が直接構築しなければならない量だ。一つの実装を作ることから、多数の実装を安全に生成できるシステムを定義することへ、作業の多くを移せる。

## プラットフォームがコントロールプレーンになる

エージェント型ワークフローでは、フロントエンドプラットフォームは生産性レイヤーだけではなく、コントロールプレーンになる。

design token は視覚的な選択肢を狭める。component API は承認された interaction pattern を提供する。schema は有効な data shape を定義する。repository instruction はローカルな制約を明示する。golden example は意図された architecture を示す。test fixture は edge case を再現可能にする。CI policy は、変更が先へ進む前にどの証拠を提示すべきかを決める。

Agent が明確な経路を速く進めるのは、その経路に人間が以前コード化した判断が含まれるからだ。経路がなければ、速度は局所的な発明を生む。ほとんど同じ component、一貫しない state model、review できない diff、そして生成された実装が自分自身と一致することしか証明しない test だ。

これにより、platform effort の価値も変わる。platform improvement は、それを覚えて使う各開発者の数分を節約するだけではない。repository に入るすべての生成変更を形づくれる。leverage は大きくなるが、悪い default のコストも大きくなる。

## 人間による実装は減り、設計された検証は増える

Agent が少ない人間の作業でより多くの変更を作るなら、検証を最後の手動作業のままにはできない。人間の review attention は、生成される出力と同じ速度ではスケールしない。

答えは、開発者により多くのコードを review させることではない。より強い証拠を設計することだ。

- frontend と backend の前提を確認する contract test
- layout と design-system drift を検出する visual regression
- semantics と interaction を確認する accessibility check
- ユーザーから見える flow を検証する end-to-end test
- 現実的な確認のための preview environment
- release 後にしか見えない挙動のための observability
- risk を限定する scoped diff、rollout control、rollback path

これらの check も開発作業だ。何が重要かを決め、failure をモデル化し、有用な境界を選び、signal の信頼性を維持するという、以前 feature implementation に使っていたのと同じ注意が必要になる。

check は多ければよいわけではない。生成された変更は、間違った問題を解決しながら浅い test を通過できる。大きな test suite は遅くなったり noisy になったりして、人が信頼しなくなることもある。どの性質を invariant にするか、どの outcome を観測するか、どの exception に注意を向けるかは、人間が決め続けなければならない。

有用な変化は、機械的な各ステップを繰り返し調べることから、一度ルールをコード化して継続的に適用することへの移行だ。

## 新しく希少になる作業

問題定義は人間の仕事として残るが、新しい役割の一部にすぎない。より大きな機会は、エンジニアリングの判断を再利用可能にすることにある。

生成前に曖昧さを解消し、チームが繰り返し意見を違える契約を強化し、また一つだけの component を受け入れる代わりに platform primitive を追加し、流出した不具合の後に検証を改善する。それに加えて、未知の risk、相反する constraint、incident、既存の control plane が信頼できる答えを持たない変更といった例外を扱う。

フロントエンド開発者への問いは、「このインターフェースを作れるか」より広くなる。システムは意図したインターフェースを生成しやすくしているか。間違ったインターフェースをリリースしにくくしているか。別の開発者、デザイナー、バックエンドエンジニア、Agent が、同じコンテキストを再構築せずに制約を理解できるか。

## 実行される技術から、コード化される判断へ

エージェント以前の時代は、高コストなプロセスを通じて有用な直感を鍛えた。開発者はもっともらしい出力を疑い、境界をまたいで挙動を追い、ブラウザが実際に何をしたかを確認することを学んだ。その教訓を偶然教えた機械的な苦労まで残す理由はない。

まもなく Agent は、人間が挙動の説明を終える前にフィルターを実装するかもしれない。残る仕事は、その説明を正確にし、Agent に境界のあるプラットフォームを与え、結果が実システム全体で成立する証拠を要求することだ。

フロントエンド開発が消えるのではない。その判断が、一つずつ変更を作る手から、多数の変更を信頼可能にするプラットフォーム、契約、検証ループへ移っている。
