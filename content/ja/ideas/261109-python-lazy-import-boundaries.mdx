[Python 3.15.0 は 2026 年 10 月 9 日に安定版として公開されました](https://www.python.org/downloads/release/python-3150/)。追加された機能の一つが明示的な遅延インポートです。本稿はその技術的な評価であり、速報や移行を実施した記録ではありません。アプリケーションの高速化率も測定していません。

考えたいのは、初期化をどこで行うべきかです。コマンドラインツールが、ユーザーがレポートを作りたいのかヘルプを見たいだけなのかを判断する前に、重いレポート用ライブラリを読み込む場合があります。遅延インポートはヘルプの経路で不要な処理を省ける一方、レポートの経路で依存先を初期化し、異常に気づく時点も変えます。

## 名前の束縛とモジュールの読み込みを分ける

[Python 3.15 の言語リファレンス](https://docs.python.org/3.15/reference/simple_stmts.html#lazy) は `lazy import module` と `lazy from module import name` を説明しています。遅延プロキシを束縛し、インポートした名前を初めて使うときに実際のモジュールを読み込みます。`from` 形式でも必要になればモジュール全体を読み込みます。要求した定義だけを選んで実行する仕組みではありません。

この構文はモジュールスコープに限定されます。関数、クラス本体、`try`／`except`／`finally` ブロック内では使えず、スターインポートと future 文も遅延できません。自動変換をレビューする際にも重要な制約です。すべての import にキーワードを足すだけでは、有効な移行になりません。

古い Python でも解析できるソースが必要なら、リファレンスには `__lazy_modules__` という選択肢があります。モジュールレベルで完全修飾モジュール名を列挙するコンテナを定義すると、3.15 では一致する通常のインポートが遅延されます。古い構文を保てても、対応する各インタープリターでの動作確認は必要です。バージョン間で読み込み時点が同じになるわけではありません。

## エラーの発生時点もインターフェースの一部

リファレンスによれば、`ImportError` や `SyntaxError` などのモジュール読み込みエラーは初回使用時に発生します。したがって、アプリケーションの入口モジュールを正常にインポートできても、遅延した依存先をすべて読み込めるとは限りません。

たとえばオプションのエクスポートコマンドなら、必要な追加依存先がない環境でコマンドを起動し、診断メッセージと終了ステータスを確認するテストが役立ちます。`--help` の成功は別の経路を検証しています。どちらも必要で、一方をもう一方の代わりにはできません。

起動時に失敗を検出すべき場所では即時インポートを保ちます。意図的に遅らせるなら、初回使用の境界でエラー処理を確認します。すべての例外を捕まえて「追加パッケージがない」と処理するのは避けます。依存先自身の初期化が壊れている可能性もあり、広すぎるフォールバックは本当の不具合を隠します。

これは提案するレビュー方法であり、本稿で Python 3.15 上の実行を検証した例ではありません。

## インポートの目的が登録処理だった場合

[PEP 810 の副作用に関する説明](https://peps.python.org/pep-0810/#how-do-lazy-imports-affect-modules-with-import-time-side-effects) は、インポート時の副作用も遅延すると述べ、読み込み順序への依存より明示的な初期化関数を勧めています。

これは、ハンドラー登録だけを目的にインポートするプラグインに影響します。その後にインポートした名前を使わなければ、登録を起こすはずの契機が訪れないかもしれません。別のテストが先にプラグインを即時インポートしていると、問題が隠れることもあります。

範囲を絞って導入するなら、まずこうしたインポートを特定します。必要な登録は即時実行のままにするか、明示的な初期化呼び出しを用意して新しいプロセスでテストします。起動性能の修正を、未レビューのプラグイン探索機構の再設計へ広げないことです。初期化順序は、以前は暗黙だったとしてもアプリケーションの振る舞いです。

## コストを負担する経路を測る

即時インポートと選択した遅延インポートを比較するときは、依存先のバージョンとインタープリター設定を固定します。環境を記録し、新しいプロセスで繰り返し測定します。既存プロセスで読み込み済みのモジュールを使う測定は、別の問いに答えます。

| 経路 | 残す証拠 |
| --- | --- |
| ヘルプなどの軽いコマンド | 有用な出力までの時間と、重い依存先が必要かどうか |
| 依存先を初めて使うコマンド | 初期化を含む全体のレイテンシーと実際のコマンド結果 |
| 依存先の欠落や破損 | 診断、終了ステータス、意図した境界で失敗したか |
| 登録に依存するコマンド | 他のテストが先に読み込まなくても必要なハンドラーが使えるか |

これらは検証項目の提案であり、ベンチマーク結果ではありません。コマンド全体が速くならなくてもヘルプの高速化には価値があり得ます。一方、初回使用の遅さが許容できないワークフローもあります。遅らせた処理を消えた処理とみなさず、そのワークフローのレイテンシー予算で判断します。

初期化の契約を理解でき、よく使う経路では不要な依存先から始めます。動作と測定結果が裏づけてから範囲を広げます。明示的な遅延インポートは、その判断箇所をレビューで見えるようにします。確認すべきなのは、どの処理が今後は遅れて起こり得るかです。
