The [November 4 Go announcement](https://go.dev/blog/jsonv2) describes `encoding/json/v2` and `encoding/json/jsontext` as stable in Go 1.27. That is a useful moment to review JSON boundaries, not a reason to replace every import at once. This is a proposed review plan; no Go migration or benchmark was executed.

## Separate two decisions

The [release notes](https://go.dev/doc/go1.27#encodingjsonv2) say the existing `encoding/json` API remains supported and preserves its behavior through the new implementation, although error text can differ. A toolchain upgrade and opting into v2 semantics therefore need separate evidence.

First record the toolchain, imports and options actually used by each boundary. Run the existing contract tests before changing imports. If a test asserts exact error wording, decide whether that wording is a public contract or an incidental implementation detail. Do not delete the assertion merely to obtain a passing build; replace it with an assertion about the required behavior when that is the intended contract.

## Test acceptance and output separately

The [v2 reference](https://pkg.go.dev/encoding/json/v2) documents rejection of duplicate object names and invalid UTF-8 by default. Those defaults make previously accepted payloads worth examining. A successful round trip generated by one serializer does not exercise the same boundary as input from another producer.

Prepare a small, synthetic corpus: ordinary requests, duplicate names, malformed text, differently cased field names, and absent, null or empty collection values. For each case, record the expected acceptance decision and decoded meaning. Separately compare emitted JSON with the actual consumer's expectations. Keep personal data, credentials and copied production payloads out of fixtures.

## Make exceptions reviewable

Migrate one boundary with an owner who can explain its compatibility requirements. If an option preserves older behavior, record the affected producer, why it is needed and the condition for removing it. Avoid a global compatibility setting that obscures which contract is still dependent on it.

Keep performance evaluation separate: pin versions, input shapes and options, then measure the workload that matters. Passing compatibility tests establishes neither a speedup nor universal safety. A useful review ends with an explicit acceptance matrix, consumer checks and a rollback decision—not just a changed import path.
